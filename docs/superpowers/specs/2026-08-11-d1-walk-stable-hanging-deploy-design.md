# 設計：walk_stable 步態吊掛空跑部署（D1 EDU 輪足實機）

**日期**：2026-08-11
**分支**：`feat/d1-edu-cpg-rl`
**狀態**：設計已與使用者逐段確認，待複審

---

## 1. 目標

把 `task6/outputs/cpg_walk_stable_d1.mp4` 那組關節軌跡，在**吊掛、腳不落地、不驅動右後腿（RR）**的條件下，於 D1 EDU 輪足實機重現，並量出每個關節的追蹤誤差。

步態參數（`cpg_walk_d1.py` 的 `GAITS["walk_stable"]` 預設值，不改）：

| 參數 | 值 |
|---|---|
| 相位 | `PHASE_WALK` = `[0, π, 1.5π, 0.5π]`（側序 RL→FL→RR→FR） |
| duty | 0.80 |
| ω | 1.4 |
| μx | 1.90 |
| μy | 1.5（→ fy=0，無橫擺） |
| x_off | −0.055 m |
| G_C | 0.12 m |

驅動 FL / FR / RL 三條腿（模擬離地量 76.6 / 76.2 / 56.5 mm），RR 全程零增益。

### 成功判準

1. 全程不觸發力矩／速度保護、不撞機構限位、不出現異常力矩
2. 取得逐軸追蹤誤差：RMS、最大誤差、相位延遲
3. 記錄 500 Hz 迴圈的超時週期數

### 明確不做

落地行走、增益調校、閉環控制、驅動輪子、RL 權重推論、足端離地量的正向運動學驗證、並排對照影片。這些留給 RR 修好之後。

## 2. 為什麼是吊掛空跑

報修報告（`task6/docs/報修報告_右後輪馬達故障_2026-08-11.md` §3.3）記錄 RR 整條腿已從 CAN 失聯（`RR.abad/hip/knee` 全部讀到 0°C／0V），存活 12/16 顆馬達。四足步態少一條腿無法落地行走，所以「不控制右後腿」不是選項而是現況。

吊掛空跑是現階段唯一能推進、且不必等原廠的路徑。它驗證的是**運動學與控制鏈路**：`calib_map` 映射正確、串流控制器穩定、關節追得上軌跡。

### 這關過了不代表落地能走

空中沒有地面反作用力。`kp=20` 在空中夠，不代表承重時夠 —— `cpg_walk_d1.py` §3 的掃描顯示 kp 掉到 60 模擬離地量就剩 37.7 mm（kp=80 是 82.9）。落地是另一個題目，前提是 RR 修好。**本文件的任何結果都不得外推到落地。**

## 3. 上機前已完成的離線量測

以下數字由離線計算取得（20 秒 / 1000 幀，`walk_stable` 預設參數），是本設計幾個決策的依據。

### 3.1 限位餘裕：膝只剩 0.65°

經 `calib_map` 轉到 SHM 慣例後，各軸距離 `ctrlrange` 的最小餘裕：

| 軸 | 餘裕 |
|---|---|
| abad | +0.4687 rad（26.9°）—— μy=1.5 使 abad 完全不動 |
| hip | +1.0751 rad（61.6°） |
| **knee** | **+0.0114 rad（0.65°）** |

膝在擺動相折到 −2.6916 rad，`ctrlrange` 下界 −2.7030，機構硬限位 −2.723（MJCF 的 `joint range` 比 `ctrlrange` 寬 0.02 rad）。所以離指令限位 0.65°、離硬限位 1.8°。

**風險**：`calib_map` 的 offset 誤差量級恰好就在這個尺度。以 `POSE_LIE` 對照 MJCF 推導的 SHM 限位，leg0 abad 超出 0.0089 rad、leg2 abad 超出 0.0138 rad（0.5～0.8°）。實機的膝很可能會頂到限位，而模擬顯示 clip 0.000%，離線看不出來。

這不是新引入的問題 —— `cpg_walk_d1.py` §1-3 已記錄 `G_C=0.14` 會造成 5.4% clip，代表 0.12 本來就踩在邊緣。差別只是先前沒人量過餘裕有多少。

### 3.2 速度需求：膝 ~15 rad/s

| 量測 | 值 |
|---|---|
| 指令軌跡連續時間峰值（1 kHz 取樣） | 15.20 rad/s（膝）／12.67（hip） |
| 模擬實際關節角速度峰值（kp=80、含地面反作用） | 16.80 rad/s，99 百分位 14.84 |

15 rad/s ≈ 145 rpm。MJCF 沒有關節速度上限（`d1_edu_w.xml` 的 joint class 只有 `range`／`armature`／`damping`／`frictionloss`），來源 URDF 不在本 repo 內未能查證，**實機馬達做不做得到是未知的**。

同時量到：模擬自己在 kp=80 下的追蹤誤差峰值 17.34°、RMS 5.88°。也就是說**影片裡看到的動作已經是被位置伺服濾過的版本**，不是指令軌跡本身。實機 kp=20 只會更鈍。

### 3.3 內插的必要性

| 寫入方式 | 單步角度變化 | kp=20 下的瞬間力矩 |
|---|---|---|
| 50 Hz 直接寫 | 0.2944 rad（16.87°） | 5.89 N·m |
| 500 Hz 線性內插 | 0.0294 rad | 0.59 N·m |

50 Hz 直寫的 5.89 N·m 逼近 L4 的 `TORQUE_ABORT=8.0`。**上取樣不是效能優化，是安全需求。**

### 3.4 起步位移

步態第 0 幀與 `POSE_STAND` 的最大差距 0.4553 rad（26.09°，leg1 hip）。需要有明確的 ramp 段，不能直接跳。

## 4. 架構

三個元件。

### 4.1 `task6/inference/gait_export.py`（離線）

```
產生（預設）：
  cpg_walk_d1.make_cpg_step + joint_targets   ← 直接 import，不複製
    → 每 20 ms 的 12 軸 MJCF 角
    → calib_map.mjcf12_to_shm
    → 五項離線檢驗
    → gait_walk_stable.npz

分析（--analyze <statelog>）：
  實機 state log → 對齊指令 → 逐軸 RMS、最大誤差、相位延遲、超時週期統計
```

只呼叫 `make_cpg_step` 與 `joint_targets`，不跑物理；但仍要載入 model 取得 `cpg_d1.leg_ik_consts` 的 IK 常數。

**不得複製 `cpg_walk_d1.py` 的軌跡邏輯。** 兩份會漂移，而漂移是靜默的。

#### npz 內容

| 欄位 | 說明 |
|---|---|
| `t` | (N,) 時間，50 Hz |
| `q_mjcf` | (N, 4, 3) MJCF 慣例，policy 腿序 |
| `q_shm` | (N, 4, 3) SHM 慣例，SHM 腿序 |
| `meta` | 步態名與全部參數、`calib_map` 內容雜湊、最大角速度、最小限位餘裕、產生時間 |

`meta` 帶的最大角速度與限位餘裕，是 L7 設定保護門檻的來源 —— 門檻由軌跡算出來，不是拍腦袋。

#### 五項離線檢驗（任一不過就不產檔）

1. **限位餘裕** ≥ 0.05 rad（2.9°）。轉換規則是 `sign × limit + offset`，且 **`sign = −1` 時上下界對調** —— `calib_map` 裡 FR/RR 的 hip、knee 都是 −1，這是最容易寫錯的一步，要有單元測試釘住。
2. 逐幀角速度最大值（寫入 `meta`）
3. 跨幀跳變連續性
4. 第 0 幀與 `POSE_STAND` 的距離（決定 ramp 時間）
5. MJCF 側 `ctrlrange` clip 率為 0

**已知：`walk_stable` 現況過不了第 1 項**（餘裕 0.0114 < 0.05）。

**決策（使用者確認）**：把 `G_C` 從 0.12 往下調並重新掃描，取「餘裕 ≥ 0.05 rad 前提下離地量最大」的值。曾考慮的替代方案是保持參數原封不動、接受膝可能頂限位並靠力矩保護擋下來 —— 不採用，因為頂限位時馬達會持續對機構硬推，靠事後中止來處理是把可預防的問題留到現場。

**代價要講清楚**：上機跑的會是微調過的 `walk_stable`，不是影片裡那組原封不動的參數。掃描結果與影片版的離地量差異要記錄下來。

### 4.2 `task6/realbot/L7_gait_shm.py`（狗上）

```
--mode jog    單關節 ±0.10 rad 三角波，錄 state → 確認正負號
--mode leg    只驅動一條腿跑完整步態，其餘零增益
--mode gait   三腿同步（--skip-legs 2）

--source {file,live}   讀 npz 播放 / 狗上即時算 CPG+IK
--time-scale <f>       時間軸縮放，同一條路徑放慢播放
--kp / --kd            覆寫增益（預設 20 / 0.7）
--confirm              真的驅動硬體（預設 dry-run）
```

`gait` 模式的動作序列：

1. 開 SHM、兩道預檢
2. 讀當前實際角 → catch 漸入（0.5 s，`p_des` 固定在當前角，增益 0 → 設定值）
3. ramp 到步態第 0 幀（時間依 §3.4 的距離算，至少 2 s）
4. 播放步態
5. ramp 回 `POSE_STAND`
6. `passive_stop` 卸力

第 3～5 段之外，全部沿用 L4 已經實機驗證過的骨架。

#### `--time-scale`

同一條關節路徑、放慢播放。速度需求等比下降，而空中本來就沒有動力學需求，所以放慢不損失任何驗證價值。

這是對 §3.2 那個未知數的正面回應：即使 1.0× 硬體做不到，也能明確講出「做得到幾倍速、瓶頸是速度還是力矩」，而不是撞牆後兩手空空。

`--time-scale 0.25` 表示四分之一速播放。實作上是對 npz 的時間軸重取樣，不是改 ω —— 改 ω 會改變 CPG 動力學而產生不同的軌跡；重取樣才能保證是**同一條路徑**。

**`--time-scale` 只支援 `--source file`。** `live` 是即時積分 CPG，放慢時間等同於降低 ω，會產生不同的軌跡（`A_CONV` 主導的振幅收斂是在真實時間裡發生的，不隨 ω 縮放）。`live` 固定 1.0×，而 §8 的 file/live 逐幀一致測試也只在 1.0× 下進行。

#### `--source live`

狗上即時跑 CPG 積分 + IK，純 numpy（車載電腦沒有 torch/onnx）。存在的理由是為之後的閉環推論鋪路，以及當作 `file` 路線的交叉驗證。**離線檔是黃金標準**，`live` 必須逐幀吻合才准使用。

### 4.3 `task6/realbot/shm_common.py`（新增，重構）

從 `L4_standup_shm.py` 抽出，L4 與 L7 共用：

- ctypes SHM 結構定義（`JointControl` / `LegControl` / `SplineCmd` / `JointState` / `LegState` / `SplineState` / `SplineData`）
- `open_shm` / `zero_all` / `set_leg_position` / `publish` / `read_leg_q`
- `preflight_mc_stopped` / `preflight_motors_healthy` / `report_legs`
- `check_guards` / `passive_stop`
- `LEGNAME` / `FAULT_BITS` / `POSE_STAND` / `POSE_LIE`

**理由**：SHM 結構定義絕對不能有兩份 —— 欄位順序漂掉是靜默的，會寫到錯的關節。相對地，L4 抽完後重跑一次趴下／站立確認的成本很低（SOP 已存在）。

**代價**：L4 被改到，必須重新實機驗證。這是抽出的一部分，不是可選項。

## 5. 增益與保護門檻

### 增益

`LEG_KP = 20 / LEG_KD = 0.7`，即 `L0_cmd_probe` 從原廠量到的站立值。空中不承重，理論上追得動，但軌跡是動態的、腿有慣量 —— 追不追得動正是這次要量的東西，所以**不預先調高**。`--kp` 保留供第二輪對照（例如 40）。

### 保護門檻由軌跡算出

| 門檻 | L4 的值 | L7 的作法 |
|---|---|---|
| `VEL_ABORT` | 2.0 rad/s | `meta` 的最大角速度 × time_scale × 1.5 |
| `TORQUE_ABORT` | 8.0 N·m | 空中逆動力學需求的峰值 × 3，且不超過 8.0 |

`time_scale` 是播放倍率（0.25 = 四分之一速），速度隨之等比下降，所以是**乘**不是除。

力矩門檻的「空中逆動力學需求」用 MuJoCo 對該軌跡跑 `mj_inverse`、機身固定、無地面接觸，取各關節峰值 —— 也就是純粹克服腿自重與慣量所需的力矩。

L4 的 2.0 rad/s 是為 2 秒 ramp 訂的，而本步態需要 ~15 rad/s（§3.2）—— 直接搬會一路誤中止。

力矩門檻反過來要**收緊**：空中不承重，重力力矩比站立時還小。空中出現大力矩只有一個意思 —— 撞到東西（吊具、限位、另一條腿）。

## 6. 關卡

每道關卡有明確的往下走條件。任一關不過就停在該關，不得跳級。

| 關卡 | 內容 | 通過條件 |
|---|---|---|
| **G0** 離線 | 五項檢驗、`file`/`live` 逐幀一致、單元測試 | 全綠才產 npz |
| **G1** `jog` | 逐軸 ±0.10 rad 微動 | 三軸方向與 MJCF 正向定義一致，人眼 + state 讀數雙確認 |
| **G2** `leg` | 只驅動 FL，0.25× → 0.5× → 1.0× | 不中止、追蹤誤差在容忍內 |
| **G3** `gait` | 三腿，0.25× → 0.5× → 1.0×，先 5 秒後 20 秒 | 同上；20 秒是為了對上模擬的 20 秒統計 |

**G1 是硬性關卡。** `calib_map.py:14-19` 明寫 hip 的正負號是暫定的、「未經吊掛驗證前不可用於閉環部署」。任一軸驗出反向就停在這裡修映射 —— 號錯的表現是腿往反方向甩到限位，而離線檢驗完全看不出來，因為數字本身很正常。

G2 選 FL 是因為它在模擬裡離地量最大（76.6 mm），最容易看出追蹤差異，同時把風險限制在單腿。

## 7. 錯誤處理

- guard 觸發、未預期例外、`Ctrl-C`（裝 signal handler）→ 一律 `passive_stop`
- npz 的 `meta` 記 `calib_map` 內容雜湊，與當前不符就拒跑 —— 防止改了校正卻拿舊軌跡去跑
- dry-run 預設、`--confirm` 才碰硬體（沿用 L4）
- RR 由 `--skip-legs 2` 排除：預檢不檢查它，但 `report_legs` 照印，讓操作者親眼確認跳過的是什麼（L4 已是此行為）
- 500 Hz 迴圈超時的週期要統計並在報告中出現。Python 在 RK3588 上跑 500 Hz 偶爾被 GC 打斷是正常的，但不記錄的話，超時造成的軌跡失真會被誤讀成追蹤誤差

## 11. 已知限制

1. **吊掛結果不能外推到落地**（§2）
2. **`walk_stable` 現況過不了限位餘裕檢驗**，需要調 `G_C` 並重新掃描（§4.1）
3. **實機馬達速度上限未知**，1.0× 可能達不到；`--time-scale` 是對此的緩解而非解答（§3.2）
4. 影片中的動作是 kp=80 伺服濾過的結果（追蹤誤差 RMS 5.88°），實機 kp=20 的實現動作會與影片有可見差異，這是預期內的，不是失敗
5. `cpg_walk_d1.py:108-110` 的註解寫「x_off 不能共用」，但程式碼中 `walk` 與 `walk_stable` 都用 −0.055 —— 對照 docstring 第 8-10 行，1.37 倍的前後離地差是**刻意接受的代價**而非 bug。本次照原樣重現，不改。註解措辭可另案釐清。
