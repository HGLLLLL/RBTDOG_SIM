## 3. reward 的演進與每一版失敗的原因

**這一節是本檔最重要的部分**：三次失敗各自暴露了一個「reward 沒有管到的自由度」，
policy 每次都精準地跑去那裡。接手的人若要再動 reward，先讀完這一節。

### v2 ❌ `W_SCUFF`（擺動相觸地懲罰）—— 罰對現象但可被規避

- 實測 scuff 0.0976 → 0.0374（−62%），FR 抬起 6.7 → 6.6 mm（**完全沒動**）
- 跨策略比對：開迴路 scuff 0.288／前腳 13.2 mm，v2 scuff 0.115／前腳 5.4 mm
  → **前腳抬得越差、scuff 反而越低**，指標與目標負相關
- 規避手法：policy 把各腿 CPG 頻率拆開（FL 2.14 / RL 1.10），耦合把相位硬鎖回去，
  結果是**穩定的相位畸變**而不是抬腳

### v3 ⚠️ 俯仰懲罰 —— 成功一半，能量搬去垂直平移

- 成功：週期俯仰 12.00° → 6.75°、omega 變異 0.378 → 0.0057、相位鎖定 R = 1.000
- 失敗：**垂直彈跳 49.0 → 89.9 mm**（惡化 1.8 倍），因為 `r_h` 用係數 40 時
  彈 90 mm 也只讓它掉到 0.9673，整段彈跳只值 0.016 分
- 後果就是使用者從側視看到的「前腳用跳的」：**FR 每週期抬起 2.03 次**。
  時序比對顯示那次多餘的小抬（26 mm）發生在機身衝到最高點 304 mm 的同一刻——
  **不是 CPG 叫它抬，是機身彈跳把支撐腳從地上拔起來**

### v4 ✅ 補垂直 + 正向抬腳獎勵

```python
W_PITCH     = 20.0   # × grav[0]^2       俯仰姿態（v3 已驗證有效，不動）
W_PITCHRATE = 0.05   # × qvel[4]^2       v3 是 0.1，砍半把速度買回來
W_OMEGA_VAR = 0.5    # × var(各腿 omega) 封住相位畸變（v3 已驗證有效，不動）
W_VZ        = 0.5    # × qvel[2]^2       ★v4：機身垂直彈跳
W_CLR       = 1.5    # × r_clr           ★v4：正向抬腳獎勵
r_h         = exp(-400 * (z - NOMINAL_HEIGHT)^2)    # 係數 40 → 400
OMEGA_MAX   = 2.5    # 4.5 → 2.5，切掉倒退走帶
```

`r_clr = mean_k( max(sinθ_k,0) × clip(clr_k / G_C, 0, 1) )`

**`clip(·, 0, 1)` 封頂是關鍵**：抬到指令高度就給滿分、再高不加分，
所以唯一還能加分的方向是把最弱的那條腿拉上來——這是 v2 那種「擺更大」規避路徑的解藥。

加 `W_CLR` 的理由（風險檢查發現的）：抬腳本身就會晃機身，`W_VZ` 與銳化的 `r_h`
**都在跟離地量作對**（開迴路掃 G_C：抬 13.9 mm 罰 0.053 → 抬 63.5 mm 罰 0.241，單調遞增）。
沒有正向獎勵的話，v4 最省事的解就是「乾脆別抬腳」，那是 v2 錯誤方向的重演。

所有權重都是照前一版的**實測原始量值**校準的，讓每項在「現在」約值 0.17~0.19
（正項總和上限 3.0）。要再加新項就照這個尺度。

## 4. ⚠️ 會騙人的指標（踩過的坑，別再踩）

1. **平均離地量分不出「四腿均勻」和「前後懸殊」。**
   v1 的 clr 是 14.6 mm 很漂亮，實際是前腳 6.8/6.8、後腳 24.6/20.0 的極端失衡。
   **一定要看每腿峰值（99 百分位），不是平均。**

2. **平均離地量還會被機身彈跳灌水。**
   開迴路掃描實測：完全不抬腳（G_C=0）且倒退走的爛步態，clr 反而是最高的 10.66 mm。

3. **互相關求相位差看不出「一個週期抬兩次」。**
   它假設訊號是單一正弦。v3 的 FL↔FR 相位差量出來是 175~185°（看似完美 trot），
   但實際 FR 每週期抬兩次。**要用「抬起事件計數 / 週期數」，或直接看時序圖。**

4. **只量旋轉會漏掉平移。** v3 就是這樣：`pitch` 和 `clr` 兩個監看指標一路改善，
   完全沒看出垂直彈跳惡化了 1.8 倍。v4 起進度列已加 `vz`。

5. **`theory` 前進量公式（`2·(2·D_STEP·fx)·ω·t`）自輪子改成會滾之後不再是上限。**
   比值 >1 是正常的。

## 5. 模型端的改動（2026-08-11，已 commit）

- **輪子不再熔接鎖死**，改成被動鉸鏈 `damping=2.0 / frictionloss=0.3`、無致動器。
  依據：實機量到原廠輪 kp=0 / kd=0.1。damping 用 2.0 而非 0.1 是因為純自由轉會讓
  開迴路推進力全被空轉掉（+5.80 m → +0.14 m）；2.0 保留推進又讓輪受力可讓。
- **nq 19 → 23、nv 18 → 22**，12 個腿關節在 qpos 裡**不連續**。
  一律用 `d1_model.LEG_QPOS_IDX / LEG_QVEL_IDX`，**不可再用 `qpos[7:19]`**。
- **keyframe 曾被靜默補零**：qpos 只寫 19 個數時 MuJoCo 不報錯、直接補零，
  結果每個關節角往後錯一格。已修，有測試釘住。
- 腿關節補上官方 `frictionloss=0.2`（取自 zsibot 官方 xgw MJCF）。

### 實機原廠增益（唯讀量測，2026-08-11）

`task6/realbot/L0_cmd_probe.cpp` 讀 `/spline_shm` 的 **cmd 區**（官方 GitHub 查無此數據）：

- 腿關節 **kp=20.0 / kd=0.7**、輪關節 **kp=0 / kd=0.1**，站立時 100% 恆定
- 力矩公式 `t = kp(p_des−p) + kd(v_des−v) + t_ff` 交叉驗算吻合到 ~0.01 N·m
- ⚠️ **kp=20 不能直接搬進模擬**：原廠把 p_des 當力矩合成把手（站立刻意留 22° 追蹤誤差、
  t_ff=0），與本專案「p_des 是真實目標」的架構不同。模擬維持 kp=80。
- **走路時的原廠增益尚未量到**（需要遙控器讓狗走一段時同步跑 `L0_cmd_probe --secs 15`）

## 6. 手調開迴路步態 `cpg_walk_d1.py`（不含 RL）

```bash
conda run --no-capture-output -n rbtdog python task6/inference/cpg_walk_d1.py --gait walk --video
```

| 預設 | FL/FR/RL/RR (mm) | 最小 | 週期俯仰 | 彈跳 | 支撐腳 | 速度 |
|---|---|---|---|---|---|---|
| `walk`（duty 0.75）| 71/70/75/74 | 69.9 | 5.61° | 30.1 | 2.80 | 0.43 |
| `walk_stable`（duty 0.80）| 77/77/57/56 | 55.6 | 5.74° | **18.2** | **3.16** | 0.51 |
| `trot`（duty 0.50）| 79/82/97/97 | **79.0** | 7.37° | 18.8 | 2.21 | **0.79** |

三個關鍵參數（每項都有實測依據，詳見該檔 docstring）：

1. **`x_off`（足端前後基準偏移）** —— 靜態量到**質心比支撐中心偏後 17 mm**，
   後腳承重 110.8 N vs 前腳 90.9 N，站著就抬頭 +1.21°。往後移即可配平。
   **不是常數**：trot 高頻用 −40 mm、walk 低頻要 −55 mm。
2. **`mu_y = 1.5`（橫向擺動歸零）** —— 原本與前後共用 1.8 會產生 ±54 mm 橫擺，
   直線走路不需要，是側偏與左右不對稱的主因。側偏 −2.45 → +0.73 m。
3. **`g_c = 0.12`** —— ⚠️ 不要調到 0.14，會讓 5.4% 的指令撞 ctrlrange 被靜默 clip。

**低步頻一定要配 walk 步態**：trot 的 duty 固定 0.5，兩腳支撐的空檔身體會下沉，
步頻越低下沉越久（彈跳 ω=2.0 的 15.7 mm → ω=1.2 的 39.4 mm）。walk 用 duty 0.75/0.80
讓三腳著地，沒有那個空檔。實作上**只改初始相位無效**——耦合項會把相位拉回去，
必須連耦合矩陣一起換，所以本檔自帶 `cpg_step`（不動 `d1_model.PHASE_OFFSET`，那是 RL 契約）。

## 7. 還沒解決的（依優先序）

### 7.1 前後離地量仍差 2.03 倍（前 57/61、後 115/87）

**這是目前最大的一條，而且再訓練也補不上。** 成因是第 6 節那個「質心偏後 17 mm」——
開迴路加 `x_off = −40mm` 後前後比從 10.6 倍收到 1.39 倍，但 **RL policy 沒有這個自由度**，
它只能調 mu 和 omega，動不了足端基準。兩條路：

- **把 `x_off` 當固定常數加進 CPG**（免費，開迴路已驗證有效，不改動作維度）← 建議先試這個
- 開放成第 13 個動作維度（要改 `ACT_DIM` / `OBS_DIM`，既有權重全部作廢）

### 7.2 航向漂移

obs 裡**沒有絕對航向**（重力只給 roll/pitch、陀螺儀只給角速度），policy 物理上無法感知
自己偏了多少。v4 側偏已從 v2 的 −5.14 m 收到 −0.67 m / 20 秒，但機制還在。
兩個解法：加重 yaw 懲罰，或移植 task4 推論端的 odom 直線控制（**不用重訓**）。

### 7.3 其他

- `f0s` 被算出來並穿過 4 個檔案但**從未被讀取**（YAGNI）
- `jax<0.10` 只是拖延（brax 0.14.2 用了已移除的 `device_put_replicated`），正解是升 brax
- `MIN_HEIGHT = 0.16` 是從 task4 等比例外推，無實驗支撐
- MJCF 的 `armature=0.01 / damping=0.1` 是假設值；官方 xgw MJCF 兩者都沒寫

### 診斷步態品質時該量什麼

| 量 | 怎麼算 | 判準 |

| 每腿峰值離地 | `geom_xpos[foot][2] − 0.0710` 的 99 百分位 | 四腿都 > 40 mm |
