# L7 吊掛空跑操作手冊 —— walk_stable 步態部署 D1 EDU 實機

**用途**：上機當下對著做。不是教學文件，判準不寫理由的長篇解釋（背景見
`docs/superpowers/specs/2026-08-11-d1-walk-stable-hanging-deploy-design.md`）。
**範圍**：`task6/realbot/L7_gait_shm.py` 吊掛空跑（腳離地）驗證追蹤誤差。**不是**落地行走。

---

## 0. 這台機器的現況（每次上機前先確認沒變）

- **右後腿（SHM `leg2` = RR）整條馬達已從 CAN 失聯**，全程零增益、不驅動。
  詳見 `task6/docs/報修報告_右後輪馬達故障_2026-08-11.md`。所有 L7 指令的 `--skip-legs`
  **預設就是 `2`** —— 不用手動加，但要知道少的是哪一條腿。
- **機器開機後約 3 分鐘就會閃紅燈並 disable 全部 16 顆馬達**，且無法自行恢復，只能斷電重開。
  **每次上機的操作窗口約 3 分鐘。** 這是預設用 `--time-scale 0.25` 搭 `--secs 5`（單次執行約
  **27 秒**，見下方換算）的原因 —— 一次開機扣掉連線、預檢時間，做得完一到兩關，不要貪心一次跑完整個階梯。

  **27 秒是怎麼來的**（`--secs 5 --time-scale 0.25`，dry-run 可重現週期數）：接住 250
  週期 + 到起始姿 1000 週期（`start_offset_from_stand`≈0.44 rad，除以 0.25 沒超過
  `RAMP_MIN_SEC=2.0` 下限，取 2.0s）+ 播放步態 9961 週期（dry-run 會印出這個數字）+
  回站姿 1000 週期，共 12211 個 500 Hz 週期 ≈ 24.4 秒；加上收尾 `passive_stop` 800 週期
  ≈ 1.6 秒、`preflight_mc_stopped` 固定觀察 0.4 秒，合計約 26.4 秒，再加上開/關 SHM、
  預檢列印等雜項開銷，實測落在 **27 秒**左右。
- 上述兩點若某次開機情況不同（例如撐得比 3 分鐘久，或 RR 忽然又有訊號），**先當異常處理，
  不要當作故障已修好** —— 除非已收到原廠回覆確認維修完成。

## 1. 上機前檢查清單（逐項打勾，缺一不跑）

- [ ] **1. 狗吊起來，四腳離地**，用手撥動確認完全不觸地（含輪子）
- [ ] **2. RR（右後腿）垂下來不會撞到吊具、其他腿、或地面**
      —— RR 全程零增益，會被重力拉到機構限位附近垂下（模型估 `hip ≈ −60°`、
      `knee ≈ +79°`），這個姿勢比站姿低很多，比其他三條腿看起來鬆垮很多，是正常現象，
      **但要親眼確認它垂下來的路徑不會卡到東西**
- [ ] **3. `mc_ctrl` 已 SIGSTOP**：`sudo kill -STOP $(pgrep mc_ctrl)`
      （停 `mc_ctrl` 後遙控器與原廠保護全失效，這是後面所有關卡能寫入 SHM 的前提）
- [ ] **4. `estop.sh` 開在另一個終端，隨手可按**：`sudo ~/estop.sh`
      直接用這支腳本，不要手動下指令代替它。它做的事：
      1) 對 `WRITERS` 清單裡的每支寫入程式送 `SIGTERM`（清單現在含 `L4_standup_shm.py`
         與 `L7_gait_shm.py`）→ 我們的程式不再舉旗 → `spline_daemon` 的 watchdog 約 10
         個週期（~20ms）內把馬達指令清零、馬達癱軟；
      2) 等 0.2 秒後**確認真的死了**——還活著就補一發 `SIGKILL` 再確認一次；
      3) **連 SIGKILL 都殺不掉的話，拒絕解凍 `mc_ctrl`**，直接印出「請立刻切斷機器人電源」
         並以非零狀態結束——因為解凍等於讓原廠運控與還活著的我們的程式同時寫同一塊指令區，
         比什麼都不做更糟；
      4) 確認死透了才 `SIGCONT` 解凍 `mc_ctrl`，恢復原廠控制。
      這幾步（尤其「確認真的死了才解凍」）是手動下 `pkill` 指令沒有的保護，不要用手動指令
      代替 `estop.sh`。
      ⚠️ **日後新增任何會寫 SHM 的工具，都必須同步把它的檔名加進 `estop.sh` 的 `WRITERS`
      清單**，否則對著新工具按 estop 只會解凍 `mc_ctrl` 而殺不掉它，重演 L7 曾經有過的缺口。
- [ ] **5. 車載電腦有 numpy**：`python3 -c "import numpy; print(numpy.__version__)"`
      （車上沒有 torch/onnx，L7 推論全程純 numpy）
- [ ] **6. 軌跡檔已複製到狗上，且 `calib_hash` 與狗上的 `calib_map` 一致**
      —— npz 的 `meta.calib_hash` 對不上狗上 `calib_map.CALIB` 就會被 L7 拒跑，這是刻意的
      （防止改了校正卻拿舊軌跡去跑）；不一致就重新用最新的 `calib_map.py` 跑一次
      `gait_export.py --export` 再複製過去

## 2. 上機前待辦：先重驗 L4（只做一次，之後跳過）

這次改動把 `L4_standup_shm.py` 的 SHM 骨架抽到共用的 `shm_common.py`（給 L4/L7 共用，
避免 SHM 結構定義存在兩份、欄位順序漂掉沒人發現）。dry-run 輸出已確認逐字元不變，
但**這是離線驗證，不能取代實機驗證**。在跑任何 L7 關卡之前，必須先用實機重跑一次
L4 的趴下／站立，確認行為沒被改壞：

```bash
sudo python3 L4_standup_shm.py --sequence lie,stand --confirm --skip-legs 2
```

通過條件：動作與重構前一致（平順接住、平順站起、無異常力矩中止）。這一步過了才進第 3 節。
只需在**這次改動後的第一次上機**做一次，之後的上機不用重跑。

## 3. 四道關卡與往下走的條件

**任一關不過就停在該關，不准跳級往下走。** 這句話尤其是對 G1 講的（見 3.2）。

| 關卡 | 指令 | 通過條件 |
|---|---|---|
| **G0** 離線 | `pytest task6/tests -q` + `python3 gait_export.py --export <path>` | 全綠、npz 產出 |
| **G1** jog | 見 §3.1：leg0 三軸 + leg1/leg3 各一軸 hip，共 5 次 `--mode jog ... --confirm` | 方向與數值佐證都與 MJCF 正向定義一致 |
| **G2** leg | `sudo python3 L7_gait_shm.py --mode leg --only-leg 1 --traj ../weights/gait_walk_stable.npz --time-scale 0.25 --secs 5 --confirm` | 不中止 |
| **G3** gait | `sudo python3 L7_gait_shm.py --mode gait --skip-legs 2 --traj ../weights/gait_walk_stable.npz --time-scale 0.25 --secs 5 --confirm` | 不中止 |
| **G3-live** | 同 G3 加 `--source live` | 不中止，且追蹤誤差與同一倍速的 `--source file` 數字一致 |

⚠️ `--mode leg` 與 `--mode gait` 的 `--traj` **是必填的**，漏了會直接被 argparse 擋下來
（`error: --mode leg/gait 需要 --traj`）。路徑是相對於你執行指令的位置。

`--source file`（預設）是播放 `gait_export.py` 寫死的軌跡檔；`--source live` 是狗上自己
即時算 CPG + IK。兩者在任何倍速下都應該送出相同的指令，所以 G3-live 是對「狗上算得對不
對、算得夠不夠快」的獨立驗證 —— **特別看 500 Hz 週期超時率有沒有比 file 模式高**，超時
造成的軌跡失真不要誤讀成追蹤誤差。

**`--time-scale` 對兩個模式都有效**，所以 G3-live 也照 0.25× → 0.5× → 1.0× 的階梯走。
（CPG 一律在未縮放的 50 Hz 網格上積分，時間縮放純粹是播放層的事，兩模式共用同一層。）

G0 是離線步驟，可以在開發機做完，上機前確認過就好，不佔 3 分鐘窗口。

### 3.1 G1：單關節微動驗號（人眼 + 數字雙確認）

**`run_jog` 是在 MJCF 空間下指令的**：程式讀 SHM 角 → 轉成 MJCF → 在 MJCF 空間做
`+0.10 rad` 三角波（一個來回）→ 每一幀再轉回 SHM 寫入。這是判準表格能直接照抄 MJCF
正向定義、不必替每個關節心算 sign 的原因——即使某軸的 `calib_map` sign 是 `−1`，只要
校正正確，操作者看到的動作方向就是表格寫的方向，不用反過來想。

**這道關卡先前的版本不是這樣**：舊版在 **SHM 空間**下指令，但判準表格用的是 MJCF 定義。
`leg0` 的 hip、knee 兩軸 `calib_map` sign 都是 `−1`，於是校正**正確**的時候，操作者在 SHM
空間看到的方向其實跟 MJCF 判準相反——照著「方向反了就是錯」的直覺去改，會把對的校正改壞。
壞掉之後，離線的五項檢驗**全部照樣通過**（`shm_limits` 用的是同一份 `CALIB`，限位跟著一起
被鏡射，兩邊互相「對上」），只有上機才會在幾秒內把髖關節慢慢推向機構限位。這就是為什麼
現在的做法要在手冊裡特別強調「MJCF 空間下指令」這件事，而不是含糊帶過。

**要驗的不是只有 leg0。** `calib_map` 的 abad sign 是「對角」而非左右鏡像（`leg0`FR、`leg3`RL
都是 `+1`；`leg1`FL、`leg2`RR 都是 `−1`），所以不能只驗一條腿再用左右對稱推論其他腿。
`hip` 是 `calib_map.py` 檔頭明寫「暫定」的那個（每條腿的 hip sign 都還沒吊掛驗證過），
是這一關真正的重點；abad / knee 的號信心較高，但既然要花的時間很短（每次 jog 約 10 秒），
G1 對 **leg0 / leg1 / leg3 的 hip 各跑一次**，並在 leg0 上把 abad 與 knee 也一併跑過
（`leg2`=RR 整條失聯，不驗）：

```bash
sudo python3 L7_gait_shm.py --mode jog --jog-leg 0 --jog-joint abad --confirm
sudo python3 L7_gait_shm.py --mode jog --jog-leg 0 --jog-joint hip  --confirm
sudo python3 L7_gait_shm.py --mode jog --jog-leg 0 --jog-joint knee --confirm
sudo python3 L7_gait_shm.py --mode jog --jog-leg 1 --jog-joint hip  --confirm
sudo python3 L7_gait_shm.py --mode jog --jog-leg 3 --jog-joint hip  --confirm
```

MJCF 正向定義（人眼比對用）：

| 軸 | 正向 |
|---|---|
| `abad` | 外張 |
| `hip` | 後擺 |
| `knee` | 伸直 |

每一軸跑完，肉眼看腿的擺動方向是否對得上表格。**同時**看終端機印出的「驗號數值佐證」——
`run_jog` 收尾會印出三行：指令的 MJCF 位移方向（恆為 `+`）、實測 SHM 位移方向（讀
`d.state.p`）、以及據此換算出「calib_map sign 預期的 SHM 方向」是否與實測一致。
**人眼與這行數字兩者都要對得上才算過**，不要只憑肉眼感覺。

### 3.2 G1 為什麼是硬性關卡，不能跳

號如果反了，腿會**往反方向甩到限位**——而這件事離線檢驗完全看不出來，因為反過來的數字本身
仍然完全正常（`sign=-1` 只是把角度鏡射，數值範圍、單位都合理，五項離線檢驗一項都不會報錯）。
唯一能抓到反號的地方就是這裡：人親眼看腿往哪邊動、對照數值佐證。**所以 G1 沒過，不准往下跑
G2/G3，沒有例外。**

**號驗錯了怎麼辦**：

1. 停在 G1，不要繼續
2. 改 `task6/realbot/calib_map.py` 裡 `CALIB` 對應項的 `sign`（例如 `leg0.hip` 的
   `(-1, -1.166)` 改成 `(+1, -1.166)`）
3. 重跑 `python3 gait_export.py --export <path>` 產新的 npz
   —— **`calib_hash` 會變**，狗上舊的 npz 會被 L7 拒絕，這是刻意的行為，不是 bug
4. 把新 npz 複製到狗上，重跑 G1

### 3.3 G2 / G3：倍速階梯

**每一關都先 `--time-scale 0.25`，過了才 0.5，再 1.0。每一級跑完用 `--analyze` 看追蹤誤差
再決定要不要往上加一級**，不要三級一次排隊跑（力矩／速度門檻是隨 `time_scale` 查表的，
上一級沒過，門檻設定對下一級沒有意義）：

```bash
python3 gait_export.py --analyze <statelog路徑> --traj ../weights/gait_walk_stable.npz
```

**建議一律帶 `--traj`**（見 §4）：有給的話 `--analyze` 會多印一欄逐軸預測 RMS，量測值
直接對照著看，不用另外查表。`--analyze` 本身可以在狗上跑，也可以把 log 帶回開發機跑，
兩邊都行（`mujoco` 只在 `--export`/`--sweep` 才會被載入）。

G2 只驅動 `--only-leg 1`（= FL，左前）。選 FL 是因為在部署用的 `G_C=0.110` 下，它在模擬裡
離地量最大（59.5 mm，FR 59.0 / RL 53.1 / RR 53.4 次之，RR 不驅動僅供參考），最容易看出追蹤
差異，同時把風險限制在單腿。**不要因為省事換成別的腿。**

G3 是三腿同步（`--skip-legs 2`，RR 自動排除）。`--secs 5` 是配合 3 分鐘窗口的快速判斷；
若同一次開機還有餘裕、且 0.25×/0.5× 都已通過，可以在最後一級加 `--secs 20` 對齊模擬的
20 秒統計窗口做正式紀錄，但**不要為了湊 20 秒犧牲關卡順序或跳過中間的誤差檢查**。

### 3.4 log 檔名與中止記錄

`--log` 不指定的話，檔名會自動帶上 `mode` / `source` / `time_scale` / 時間戳（例如
`l7_log_gait_file_0.25x_20260812_153000.npz`），所以 **G3-live 不會蓋掉 G3 的結果**，同一級
重跑也不會互相覆蓋。話雖如此，**每一級跑完、開下一個 SHM 連線之前先把 log 收好**（複製離開
狗，或至少記下檔名），因為開機窗口短、下一輪很容易忘記上一份在哪。

log 現在有 `stage` 欄位（0=接住／1=到起始姿／2=播放步態／3=回站姿），`--analyze`
**只統計 `stage==2` 那一段**。原因：接住與 ramp 段的角速度、加速度都跟步態本身無關，混進
RMS 會把數字系統性稀釋——實測 1.0× 配 `--secs 5` 若不過濾 stage，RMS 會被稀釋 27%。所以
拿到的逐軸 RMS 已經是「純播放步態」的數字，不用自己再去掉頭尾。

**中止時（保護觸發、例外、Ctrl-C）現在也會寫 log**，檔名加 `_ABORTED` 後綴，不會跟正常收尾
的 log 撞名。撞到門檻時**不要只看終端機印出的那一行原因**，把 `_ABORTED` log 叫出來看
`cmd`/`p`/`v`/`tau`——觸發前那幾個週期的完整數據是診斷價值最高的一次。

## 4. 每一級的模擬預測值（原廠增益 kp=20 / kd=0.7）

`--analyze --traj <npz>` 會自動查表印出下面這些數字（見 §3.3），這裡列出來是給不方便帶
`--traj` 時的備查，以及先熟悉數字長什麼樣。**這是逐軸 RMS，不是單一數字**——`gait_export`
的 `meta.air_sim` 同時存了 12 軸 aggregate 與逐軸兩種統計，兩者不能拿來互相對比：拿逐軸量測
去對 aggregate（例如 1.0× 的 9.30°）會同時觸發「hip 太大」與「abad 太小」兩條假警報。

**0.25×**（力矩峰值 4.27 N·m、門檻 8.53）

| SHM 腿 | abad | hip | knee |
|---|---|---|---|
| leg0 (FR) | 5.77 | 5.26 | 6.60 |
| leg1 (FL) | 5.77 | 5.26 | 6.60 |
| leg2 (RR) *(不驅動)* | 5.75 | 5.26 | 6.59 |
| leg3 (RL) | 5.75 | 5.25 | 6.61 |
| **2026-08-12 實測** | **6.16–6.47** | **5.07–5.79** | **5.54–5.68** |

**0.5×**（力矩峰值 5.80 N·m、門檻 11.60）

| SHM 腿 | abad | hip | knee |
|---|---|---|---|
| leg0 (FR) | 6.39 | 6.81 | 9.07 |
| leg1 (FL) | 6.39 | 6.81 | 9.04 |
| leg2 (RR) *(不驅動)* | 6.35 | 6.79 | 9.03 |
| leg3 (RL) | 6.37 | 6.80 | 9.07 |
| **2026-08-12 實測** | **5.49–6.70** | **6.39–6.93** | **8.11–8.38** |

**1.0×**（力矩峰值 9.40 N·m、門檻 18.79）

| SHM 腿 | abad | hip | knee |
|---|---|---|---|
| leg0 (FR) | 6.70 | 12.30 | 11.25 |
| leg1 (FL) | 6.73 | 12.18 | 11.21 |
| leg2 (RR) *(不驅動)* | 6.67 | 12.22 | 11.27 |
| leg3 (RL) | 6.72 | 12.33 | 11.26 |
| **2026-08-12 實測** | **5.95–7.11** | **11.93–12.34** | **10.52–10.74** |

單位是度（RMS）。**`leg2`(RR) 那一列不驅動**，是模擬的完整輸出，僅供參考。
最後一列是 2026-08-12 首次吊掛的實測值（三條驅動腿的區間），**預測與實測全部落在 2–12% 內**。

⚠️ 這組預測值是 2026-08-12 修掉「機身固定」bug 之後的。修正前模擬完全沒有重力
（每步自由落體），0.25× 的 abad 只預測 0.46° 而實機是 6.3°，差 13 倍；
力矩門檻也因此訂得太緊（0.25× 原本 4.67 N·m，實機峰值 3.73，擦邊過）。
若哪天這些數字又變回「abad 只有零點幾度」，就是那個 bug 又回來了。

**一個值得留意的規律**：0.25× 與 0.5× 時誤差最大的軸是 knee，但到了 1.0× 換成 hip 超過
knee。往上加倍速時（尤其 0.5× → 1.0×）要特別盯著 hip 這一軸的量測值，不要只沿用低速時
「knee 最容易出問題」的直覺。

**另一個規律**：`abad` 三個倍速幾乎不變（都是 ~6.3°）。那是靜態重力沉降，不隨速度縮放——
這個步態的 abad 依設計恆定不動（μy=1.5），量到的完全是重力把吊著的腿往內拉的量。
所以放慢速度救不了它，只有提高增益可以（見下）。

### 4.1 提高增益（kp=40 / kd=1.0）

2026-08-12 實測 0.5×，kp 加倍的效果：

| 軸 | kp=20 實測 | kp=40 實測 | 改善 | kp=40 預測 |
|---|---|---|---|---|
| abad | 5.49–6.70 | **3.17–3.82** | −42% | 3.78 |
| hip | 6.39–6.93 | **4.30–4.56** | −34% | 3.77 |
| knee | 8.11–8.38 | **5.29–5.51** | −35% | 5.82 |

相位延遲同時從 hip 46–48 / knee 54–56 ms 降到 **34 / 38–40 ms**。
力矩峰值 5.11 → 6.39 N·m（門檻 15.83，用掉 40%）。

指令加 `--kp 40 --kd 1.0` 即可。

⚠️ **`kp=40` 不要跑 1.0×**：那一級的力矩門檻會算到 28.21 N·m，超過 `TAU_MAX=28`
（URDF effort 的保守值），等於沒有有效的力矩保護。程式目前不會擋這個，需自行避開。

**`abad` 軸的延遲欄位會顯示「—」，這是正確行為，不是故障。** `walk_stable` 的 abad 依設計
恆定不動（`μy=1.5` → `fy=0`，沒有橫擺），指令本身不動的軸，相位延遲沒有定義，`--analyze`
用 `None` 表示、印成「—」，不要當成分析失敗或漏算。

**判讀方式**：

- **實機誤差顯著大於預測** → 代表實機比模型軟：增益沒真的生效（例如 `--kp/--kd` 沒吃到、
  或原廠站立值跟 SHM 實際寫入不一致），或馬達到了速度上限撞牆（呼應 §6 的「實機馬達速度
  上限未知」）。先查增益有沒有真的寫進 SHM，再查速度上限。
- **實機誤差顯著小於預測** → **先別高興**，代表軌跡很可能沒有真的送出去（例如卡在某個
  guard、或寫入的其實是零/舊值）。先確認 state log 裡的指令角真的隨時間變化、跟 npz 對得
  上，再相信這個「表現超預期」的數字。

門檻表由 `gait_export` 匯出時算好寫進 npz 的 `meta`，L7 直接查表；查不到對應的
`(kp, kd, time_scale)` 組合會拒跑，這不是 bug，是刻意設計成「門檻不能用猜的」。

## 5. 收尾

任何一次上機結束（不論成功、中止、還是被 estop）：

```bash
sudo kill -CONT $(pgrep mc_ctrl)
```

解凍運控，恢復原廠控制。**每次離開狗之前務必確認這一步做過**——`mc_ctrl` 沒解凍的話，
下次遙控器不會有反應，容易誤判成又是硬體故障。

## 6. 已知限制（判讀對齊設計文件 §11，不要淡化）

1. **吊掛結果不能外推到落地。** 空中沒有地面反作用力，`kp=20` 在空中夠，不代表承重時夠。
2. **上機跑的是 `G_C=0.110`，不是影片版的 `0.12`**（膝關節限位餘裕從 0.65° 提到 3.95°）。
   看到的動作跟 `cpg_walk_stable_d1.mp4` 不會完全一樣，這是刻意調整過的結果，不是誤跑錯參數。
3. **實機馬達速度上限未知，1.0× 可能達不到。** `--time-scale` 是緩解，不是解答。
4. **1.0× 的預測誤差峰值 39.20°，實機動作會與影片有明顯差異。** 影片本身是 kp=80 伺服濾過
   的版本（RMS 5.88°），實機用原廠站立值 kp=20 只會更鈍。**這是預期內的，不是失敗。**
5. **`cpg_walk_d1.py` 的 `x_off` 在 `walk` 與 `walk_stable` 兩個步態共用同一個值**，程式內的
   註解寫著「不能共用」，但實際上兩者都是 `−0.055`——對照原始 docstring，前後腿離地量
   1.37 倍的差異是刻意接受的代價，不是 bug。本次照原樣重現，不改。
