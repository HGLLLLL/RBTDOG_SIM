## 部署到實機需要知道的關鍵事實

```
控制鏈：mc_ctrl → /dev/shm/joint_cmd → joint_shm_controller → zsi_actuator_driver → 馬達

座標鏈：MJCF 關節角 ＝ 控制器角 → × side_sign + offset → joint_cmd（馬達座標系）
```

| 事實 | 值 |
|---|---|
| `joint_cmd` 結構 | base=752、stride=112，`name[64]` + pos/vel/effort/kp/kd（f64） |
| **心跳（必寫）** | `base+0` 的 u64，~1 kHz。**不寫會被判過期而清零** |
| 寫入順序 | **先 payload、最後心跳**（心跳＝「這幀備妥了」的旗標） |
| SHM 腿序 | `fl, fr, bl, br` ← **與動作設定檔的 `FR,FL,RR,RL` 不同，按名稱對應** |
| 原廠 RL 增益 | ABAD 60 / HIP 120 / KNEE 120 / Kd 1.0；輪 60 / 0.5 |
| 逾時保護 | `joint_cmd_timeout: 500 ms` → 我們的程式若當掉，controller 接手套 `estop_kd=35` |
| 四元數順序 | **xyzw** |
| 輪半徑 | 0.0961 m（碰撞網格實算） |
| 輪摩擦 | 0.15 N·m 純庫倫（`damping` 應維持 0） |
| 站姿（遙控器） | `stand`：hip ±0.6 / knee ∓1.2，機身離地約 0.535 m |
| 膝模式切換 | 只翻**後兩腿**的 hip/knee 號，前腿不動。預設是**後腿往前彎** |

## 給 CPG 那條線的三個既有問題（不是我們改出來的）

由 frictionloss 那個 session 在 commit `ad1f068` 上發現：

1. **`trot` 與 `walk` 用預設值 100% 跌倒**（加摩擦前就是），只有 `walk_stable` 走得動
2. **`max_model.NOMINAL_HEIGHT` 過時約 10 mm**（實測 449.3 vs 常數推算 459）
   → **會被 CPG 的抬腿指令直接吃掉**，建議重量一次
3. **`speed` 指標嚴重低估**：是 x 位移/時間，但步態偏航 47° 走弧線
   → 真實路徑速率 0.397 vs 帳面 0.303 m/s。建議加一個路徑長輸出
4. `cpg_walk_max.py` docstring 提到的 `--sweep` 旗標在 argparse 裡不存在

另外：`--wheel-friction` 旗標的守衛是 `if wheel_friction > 0`，**只能加不能減**。
XML 已填 0.15，**無法再用旗標回到「無摩擦」**，只能改 XML。

## ⚠️ 這個 task 最重要的一條方法論

**「診斷輸出騙人」在這個 task 出現了七次。** 每一次都是量測／診斷工具本身有錯，
而不是被量的東西有問題：

1. `set -u` + `source` 別人的環境腳本 → 失敗偽裝成正常結束（還被 `2>/dev/null` 吞掉）
2. 自動判讀的 grep 打到腳本自己印的區段標題 → 誤報命中
3. `set -o pipefail` + `cmd | grep -q` → SIGPIPE 造成誤報失敗
4. `tick_end` 在 `restore()` 之後才讀 → 心跳速率算錯 15%
5. 輪角沒解纏（讀數包裹在 ±π）→ 轉超過半圈時連方向都算反
6. 保護用了雜訊訊號（`velocity` 欄位）→ 假尖峰造成誤中止
7. 拿**馬達座標系**的角度去比 **URDF/MJCF 的限位** → 憑空生出「超限」

**共同的解法：多印一個可以互相對照的量，比多印一個結論有用。**

正面例子（第 7 次之後）：驗證座標系時，「四輪共面」看起來足以定案，
但同時算了「MJCF 限位」與「對文件姿勢的 RMS」——才發現**共面性對 V1/V3 沒有鑑別力**。
只看一個指標就會選錯。

其他反覆用到的：
- `pgrep -f` / `pkill -f` 的 pattern 別包含自己的命令列（task6 中過兩次，殺掉自己的 SSH）
- 比較兩個量之前，先確認**同座標系、同單位**
- 單次模擬結果可能是雜訊（trot 對微擾是混沌的，速度差 4 倍）——只採信穩健趨勢
