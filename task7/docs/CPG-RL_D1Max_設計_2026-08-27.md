## 0. 為什麼做這件事

開迴路 `walk` **走得穩但走不直**：180 秒 × 12 擾動 0 跌倒，
但偏航 −0.5 ~ −0.9 °/s，180 秒累積 −51°、側偏 −10.7 m。

而且**調參繞不過去**（三個獨立證據）：

- `x_off` 在 20 mm 範圍內掃，偏航率 −0.858 ~ −0.814 °/s，**完全不變號**
- `d_step` 單調（0.100→−0.06、0.130→−0.85 °/s），**沒有過零點**
- `ω` 在 1.8 變號（+0.68）但 2.0 又變回來（−0.87）—— **那是分歧不是趨勢**

航向只能靠回授。而 RL 拿得到 gyro，這正是它該做的事。
**所以這一輪要打敗的主要是偏航，速度是附帶的。**

### 1.1 刻意排除的三項

| 排除 | 理由 |
|---|---|
| **機身線速度** | 底層沒有這個量。高層 SDK 有，但凍結 `mc_ctrl` 後高層就死了。reward 仍用模擬真值 —— reward 只在訓練時計算，訓練產物只有 policy 權重，推論時一行都不會執行到 |
| **足端觸地** | 沒有感測器。task6 在同型輪足（D1 EDU）實測四個候選訊號**全部不可用**：0.9 kg 的輪子讓**擺動相**的膝力矩與位置誤差**大於站立相**，訊號方向是反的（膝力矩站立相 p05=1.55 N·m、擺動相 p95=8.76）。D1 Max 的輪更重（**1.51 kg**），只會更嚴重 |
| **輪子角速度** | 實機讀得到，但實機**從未走過路**，輪速在真實地面（地毯 vs 磁磚）的行為零資料可對照，而 policy 又控制不了它（輪子固定阻尼）。放進去等於押一個沒驗證過的量 |

有測試釘住「機身線速度不在 obs 裡」（`test_obs_excludes_base_linear_velocity`），
擋的是「訓練時順手加一欄讓 reward 好學、上機才發現餵不出來」。

### 1.2 ⚠️ 上實機前的硬性前提：IMU 尚未驗證

`/dev/shm/imu_central` 目前**只有 2026-08-25 一次離線快照解碼過，
沒驗過是不是活的串流**（`joint_state` 的 1 kHz 活性是驗過的，IMU 沒有）。
而且 `xyzw` 順序是「取樣當下機身剛好水平」推出來的，**不是刻意做的平放實驗**。

四元數順序若錯 → 重力向量整個翻掉 → **policy 直接廢掉**，
而且症狀不是報錯，是「狗一走就往某個方向倒」，
現場會被誤判成「RL 沒訓練好」而去改訓練。

→ **上機前先跑 `task7/docs/現場操作卡_IMU平放複核.md`**（唯讀、零風險、15 分鐘）。
本次已補上 `shm_io.read_imu()` 與欄位位移的回歸測試（`test_shm_imu.py`）。

## 2. 動作空間：12 維

每腿 `(mux, muy, omega)` → `tanh` → 線性映射。輪子**不進動作空間**，維持純阻尼
（給位置增益實測造成 **+39° 偏航失控**）。

| | 範圍 | 依據 |
|---|---|---|
| `mu_x`, `mu_y` | 1.0 – 2.0 | 沿用 task4 / task6 |
| `omega` | 0.0 – 2.0 | ω=1.8 → 0.316 m/s 但彈跳 +48%、支撐腳 −0.3；ω=2.0 速度反而掉回 0.281 |

### ★ 與 task6 最關鍵的差異：`duty` 必須進 env

task6 的 env **沒有 `duty_remap`**（等效 duty=0.5），
而 D1 Max 實測 **`duty ≤ 0.70` 是 12/12 全跌**。
照抄 task6 的 env 會得到一台永遠站不住的狗，而且不會有任何錯誤訊息。

env 內完整沿用 task7 的軌跡鏈：

```
cpg_step → duty_remap(0.80) → foot_targets(x_off=−40mm, z_sag=32.5mm 只加擺動相)
         → 每腿各自的 home_foot + knee_sign → 解析式 IK → 12 個關節目標角
```

- **解析式 IK**，不是 task6 的線性化 Jacobian：這台抬腿 100 mm、連桿 0.26+0.28 m，
  線性化誤差會直接汙染「抬腿量」—— 而那正是 reward 的 `r_clr` 要獎勵的東西。
- notebook 內建 **JAX vs numpy 的逐點對照**（容差 1e-4 rad ＝ float32 捨入；
  開 `jax_enable_x64` 實測差 **2.2e-16**）。沒有這個檢查，移植錯一個號會安靜地
  變成「訓練與推論是兩台機器人」，而訓練曲線會很漂亮 —— 因為 policy 只是學會了另一台。

## 4. Reward、終止、domain randomization

### 4.1 Reward

移植 task6 reward v4 的全部懲罰項（權重都經實測校準）＋ 偏航率追蹤。

| 正項 | 權重 | |
|---|---|---|
| 前進速度追蹤 `exp(−(vx−cmd_vx)²/0.02)` | 1.5 | |
| **偏航率追蹤 `exp(−(wz−cmd_wz)²/0.05)`** | **1.0** | ★ 本輪主目標 |
| 側向速度 `exp(−vy²/0.02)` | 0.5 | |
| 機身高 `exp(−400(h−0.4825)²)` | 0.5 | 目標用**走路時**高度，不是靜態站立的 0.4493 |
| 抬腳 `r_clr` | 1.5 | 封頂在 `G_C`：抬到位就給滿分，再高不加分 |

| 罰項 | 權重 | 針對 |
|---|---|---|
| `grav[0]²` | 20.0 | 機身俯仰姿態 |
| `qvel[4]²` | 0.05 | 俯仰角速度 |
| `qvel[2]²` | 0.5 | 機身垂直彈跳（v3「打地鼠」打出來的洞） |
| `var(各腿 ω)` | 0.5 | ★ 封住「把各腿頻率拆開」這個規避管道 |
| `Σ(Δaction)²` | 0.01 | 動作抖動 |
| `Σtau²` | **3e-5** | 見下 |

★ **力矩懲罰係數是量出來反推的，不是沿用**：基準步態在這個動作空間裡是一個
**固定動作**（`mux/muy/ω` 用 `atanh` 反推），直接跑它量到 `Σtau²` 中位數 **1648**。
取 3e-5 讓這一項在「已知可行的步態」上值 **0.049 分**（正項總和上限 5.0，約 1%）。
task6 的 5e-6 只值 0.008 分，**等於這一項不存在** —— 那台的力矩上限只有 33 N·m。

⚠️⚠️ **其餘權重仍是照 D1 EDU（20.6 kg）訂的。這台 41 kg，第一輪訓練後必須依
`progress` 印出的實測值重新校準**，不要當成定案。task6 就是這樣從 v1 迭代到 v4 的。

**reward 可以用上帝視角，obs 不行**：`r_clr` 用 `geom_xpos` 真值，實機沒有這個訊號，
但 reward 只在訓練時計算、訓練完就丟棄。

## 5. 訓練規模

PPO（brax `0.14.2` / MJX），**版本鎖死不放寬** ——
brax 載到 activation 不匹配的權重**不會報錯**，只會讓 policy 靜默錯亂，
而 activation 由 brax 的**版本**決定。

`num_envs=2048`、`episode_length=1000`（20 s）、`batch_size=256`、
`num_minibatches=32`、`unroll_length=20`、`lr=3e-4`、`entropy_cost=1e-2`、
`discounting=0.97`、`normalize_observations=True`、
policy `(256,256,128)` / value `(256,256,256)`，先設 **60M steps**。

⚠️ **成本預告**：`SIM_DT=0.002`，每控制步 **10 個物理步**（task6 是 5）→
每步計算量約 **2 倍**。notebook 的 `progress` 在第一個 eval 就印出實測步率與
「60M 約需幾分鐘」，**當場決定要不要砍到 40M**，不要硬等。

已在本機用極小規模（8 env / 4096 步）實跑 PPO 驗過契約：
8 個 metrics 鍵全部出現在 `eval/episode_*`，`domain_randomize` 的 `in_axes` 結構也過。

### 6.3 ★ 判讀這批數字時踩到的坑（差點寫成假結論）

第一次量轉彎，得到「`wz=+0.3` → 偏航率 **−6.77 °/s**」，兩個方向都反 ——
看起來就是「偏航指令接反了」這種很有說服力的 bug。

**實際上是量測錯了。** `yaw_deg` 用 `atan2`，值域 (−180, 180]。
下轉彎指令時 20 秒就轉超過一整圈，**首尾相減會包裹**：
真實 +224.6° 被讀成 −135.4°，連符號都翻掉。

開迴路直走時總偏航 < 60°，永遠不會包裹，所以這個坑一直沒露出來 ——
**它是「接上回授之後才會出現」的那類錯誤**。

→ 已修：`Trace` 新增 `yaw_total`（逐步累加、折回 ±180 的增量），
   `local_infer_max` 的 `yaw_rate` 改用它，並加了不依賴物理的回歸測試
   `test_yaw_total_survives_wrapping`。
   `yaw`（首尾相減）保留但已標註「只在總偏航 < 180° 時可用」。

### 已通過的一條額外驗證

`local_infer_max.py --dummy` 跑出來的**八個指標與開迴路 `rollout` 逐位相同**
（`speed_travel / bounce / pitch_mean / support / yaw / net_roll / min_lift / height`）。

這條之所以做得到，是因為**基準步態在這個動作空間裡就是一個固定動作** ——
所以整條推論鏈（obs → `act_to_cmd` → CPG → 解析 IK → PD）有**標準答案**可對，
而不是「跑起來沒炸就算過」。任何一個係數、順序、映射範圍接錯都會在這裡露餡。
