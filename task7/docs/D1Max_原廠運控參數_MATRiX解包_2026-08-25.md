- 日期：2026-08-25

- 原始檔已收進 `task7/reference/matrix_zgws/`，取得方式與可信度說明見該目錄的 `SOURCE.md`
- 機型對應：**`ZGWS` = `zg_wheels` = `zsm-1w` = D1 Max**

## 0. 為什麼這份文件重要

它把 `HANDOFF_CPG步態_起步交接.md` §6「必須重新決定的參數清單」裡**一半以上的項目
直接給了答案**——而且不是規格書上的公稱值，是原廠運控**實際在跑**的那組數字。

**可信度**：`xg_wheel`（D1 EDU）那份的 `FSM_RL_*` 增益與 task6 在實機 `/spline_shm`
量到的原廠值**逐項吻合**（腿 kp=20 / kd=0.7、輪 kd=0.1）。
→ 這批設定檔就是實機在用的參數。但 D1 Max 本身**尚未上實機驗證**，
所以全篇標示為**高信心推定**，不是已實測。

|---|---|---|---|---|---|---|
| **RL 策略（走路用）** | **60** | **120** | **120** | **1.0** | **60** | **0.5** |
| RL 平衡站立 | 60 | 60 | 60 | 1.0 | 20 | 0.5 |
| 關節 PD（FSM） | 250 | 250 | 250 | 5.0 | — | — |

| 自主充電 | 400 | 400 | 400 | 5.0 | — | — |
| Passive（洩力） | — | — | — | 16.0 | — | 0.1 |
| 低功耗 | — | — | — | — | 0 | 0 |

**與 D1 EDU（task6 那台）對照：**

| | D1 EDU (`xg_wheel`) | **D1 Max (`zg_wheels`)** | 倍數 |
|---|---|---|---|
| RL ABAD Kp | 20 | **60** | 3× |
| RL HIP / KNEE Kp | 20 / 20 | **120 / 120** | **6×** |
| RL Kd | 0.7 | **1.0** | 1.4× |
| RL 輪 Kp / Kd | 5 / 0.1 | **60 / 0.5** | 12× / 5× |
| Passive Kd | 4.0 | **16.0** | 4× |
| 關節 PD Kp | 130 | **250** | ~2× |

⚠️ **ABAD 與 HIP/KNEE 是不同的 Kp（60 vs 120），不是四個關節共用一個值。**
task6 的 D1 EDU 三個腿關節共用 20，這台不是。寫 MJCF 的 actuator 時要分開設。

⚠️ **輪子在 D1 Max 上是「真的有位置增益」的**（RL 用 Kp=60），
不像 D1 EDU 幾乎只做阻尼（Kp=5）。這台的輪子在走路時是被主動控制的。

## 2. 姿態與尺寸

| 參數 | 值 | 說明 |
|---|---|---|
| `body_height` | **0.48 m** | 站立時機身高度（D1 EDU 是 0.38） |
| `leg_height` | **0.1 m** | **抬腿高度** ← 直接對應 CPG 的 `g_c` |
| `body_half_length` | **0.27 m** | ✅ 與 URDF 髖 x = ±0.272 吻合 |
| `drop_height` | −0.22 m | |
| `feet_z_offset` | 0.095 m | ⚠️ 不等於輪半徑 0.09，是運控自己的偏移慣例 |

### 關節目標姿（控制器座標系，腿序 FR / FL / RR / RL）

| 姿態 | ABAD | HIP | KNEE |
|---|---|---|---|
| **站立** | `[0, 0, 0, 0]` | `[0.6, 0.6, −0.6, −0.6]` | `[−1.2, −1.2, 1.2, 1.2]` |
| **趴下** | `[0, 0, 0, 0]` | `[1.4, 1.4, −1.4, −1.4]` | `[−2.4, −2.4, 2.4, 2.4]` |
| **RL 預設姿** | `[0, 0, 0, 0]` | `[0.8, 0.8, −0.8, −0.8]` | `[−1.5, −1.5, 1.5, 1.5]` |

**★ 這是跟 D1 EDU 最重要的一個結構差異：**
D1 EDU 四腿同號（`hip_stand_pos = [0.8, 0.8, 0.8, 0.8]`），
**D1 Max 前兩腿與後兩腿反號**（`[0.6, 0.6, −0.6, −0.6]`）。
也就是站姿是**前後鏡像的 X 型**，不是四腿朝同一方向。

→ 做 IK 與 CPG 時，**「四條腿套同一組公式」的假設在這台會失效**。
task6 的 `HOME3` 是四腿共用一組 `[0, 1.05, −2.00]`，這台必須是每腿各自
（或前後兩組）。`d1_model.LEGS` 那種「四腿同號」的寫法照抄會錯。

⚠️ 這是從設定檔數值推出來的結構結論。**MJCF 建好後請用靜態站立驗證一次**
（把上面的站姿角度餵進去，看四條腿是不是撐得住、機身高度是不是 ~0.48 m）。

## 3. 符號與零點慣例（sim2real 校正層用）

```
腿序：FR, FL, RR, RL

abad_side_sign   : [-1, -1,  1,  1]
hip_side_sign    : [ 1, -1,  1, -1]
knee_side_sign   : [-1,  1, -1,  1]
wheel_side_sign  : [ 1, -1,  1, -1]

abad_offset      : [ 0.523, -0.523, -0.523,  0.523]
hip_offset       : [-2.443,  2.443,  2.443, -2.443]
knee_offset      : [-2.803,  2.803,  2.803, -2.803]
wheel_offset     : [0, 0, 0, 0]
```

**觀察**：offset 的絕對值 = URDF 的關節限位（abad 0.523、hip 2.443、knee 2.803）
→ 看起來是「馬達編碼器零點落在關節機構限位處」的慣例。

⚠️ **但 `控制器角度 = side_sign × 馬達角度 + offset` 這個公式我沒有原始碼佐證，
是從數值形狀推的。上實機前必須逐關節驗一次。**
task6 在 D1 EDU 上就是踩過這個坑——「站姿 ≈ MJCF home」的假設做出一組
**自洽但錯誤**的映射，所有檢查都過，實機一動就錯（見記憶檔 `d1-edu-calibration-lessons`）。

⚠️ `abad_side_sign = [-1, -1, 1, 1]` 是**前後分組**（前兩腿 −1、後兩腿 +1），
不是左右分組。task6 的 D1 EDU 是 `[-1, -1, 1, 1]` 同樣形狀（被稱為「對角型」），
但 `knee_side_sign` 兩台**正負相反**（D1 EDU `[1,-1,1,-1]`、D1 Max `[-1,1,-1,1]`）。

## 4. 限位與速度上限

| 項目 | 設定檔 | URDF / 規格書 | 用哪個 |
|---|---|---|---|
| ABAD 限位 | ±0.873 (±50°) | 右 −0.697~+0.523、左 −0.523~+0.697 | **用 URDF**（設定檔那組是保護外圍值） |
| HIP 限位 | ±2.80 | ±2.443 | **用 URDF** |
| KNEE 限位 | ±2.775 | ±2.801 | 兩者接近，取小的 |
| 關節速度上限 | **24.0 rad/s** | URDF 沒填；規格書 190 RPM ≈ 19.9 rad/s | ⚠️ 兩者不一致，保守取 **19.9** |
| 控制頻率 | `controller_dt = 0.002` → **500 Hz** | — | — |

⚠️ **URDF 的 ABAD 限位是左右鏡像且不對稱的**（右 −0.697~+0.523、左 −0.523~+0.697），
設定檔的 ±0.873 是對稱的。做 IK 限位檢查一定要用 URDF 那組，而且**逐腿檢查**。

## 6. 這份文件如何改寫「必須重新決定的參數清單」

`HANDOFF_CPG步態_起步交接.md` §6 的表格請照這裡更新：

| 參數 | 交接文件原本寫 | **現在有答案了** |
|---|---|---|
| `KP` / `KD` | 「先從模擬掃描找」 | **ABAD 60 / HIP 120 / KNEE 120，Kd 1.0；輪 60 / 0.5** |
| `HOME3` | 「重算」 | **站姿 hip ±0.6 / knee ∓1.2；RL 預設姿 hip ±0.8 / knee ∓1.5。前後反號！** |
| `NOMINAL_HEIGHT` | 「重量測」 | 起點用 **0.48 m**，再扣位置伺服的靜態撓度 |
| `G_C`（抬腳高度） | 「重掃」 | 起點用 **0.10 m**（原廠 `leg_height`） |
| 關節速度上限 | 「用 19.9」 | 設定檔寫 24.0，**兩者不一致，保守仍取 19.9** |
| 腿序 | 「自己選一個寫死」 | 原廠是 **FR, FL, RR, RL**（`motion_config` 裡寫死），**建議直接跟它一致** |
| `CTRL_DT` | 「先用 50 Hz」 | 原廠運控是 **500 Hz**；50 Hz 出指令仍可，但別假設底層也是 50 |

**仍然要自己掃的**：`x_off`（質心配平）、`mu_y`、`D_STEP` / `D_STEP_Y`、`OMEGA` 區間。
這幾個跟步態本身的動力學綁在一起，原廠設定檔沒有對應項。

## 7. 附帶發現：原廠策略檔（不能用，但值得知道存在）

`assets-0.1.2.tar.gz` 的 `src/robot_mc/build/export/onnx_model_crypto/zg_wheels/` 底下有
20 多個 ONNX 策略，檔名與 D1 Max SDK 的高層動作 API 一一對應：

```
policy / policy_gait_walk / policy_skwalk / policy_stair / policy_climb / policy_slim
policy_dsb / policy_snow / policy_zgws_rpy / policy_zgws_jump / policy_zgws_backflip
policy_handstand / policy_tuoluo / policy_tuoluo_singleg / policy_mix_flipover
policy_zgwt_crawl_1029
（每個 policy_* 都有對應的 odom_*）
```

**它們是加密的**（同目錄有 `libfilecrypto_shared.so` 與 `file_crypto_cli`），沒有金鑰讀不出來。
所以「直接拿原廠 policy 來跑」這條路走不通，不用花時間試。

但這份清單本身有兩個用處：
1. 證實 SDK 高層那些動作（`Slim` / `DSB` / `Stair` / `SkWalk` / `Climb` / `Sand`）
   **底下都是 RL 策略**，不是寫死的軌跡 → 這台的運控本來就是學出來的。
2. `policy_gait_walk` 的存在說明官方走路也走「gait + walk」這條路，
   跟我們要做的 CPG 步態是同一類問題。
