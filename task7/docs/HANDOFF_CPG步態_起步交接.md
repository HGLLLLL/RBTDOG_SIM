## 3. 目前卡在哪 / 不卡在哪

**不影響你開工的**：模擬端的一切。URDF 已經有了，機構參數齊全，可以直接做 MJCF 與 CPG。

**尚未定案的**：實機的**底層寫入介面**。官方 SDK 只開放高層（`Move(vx,vy,yaw)` 百分比速度），
送不了關節角度。底層可能存在於 ROS2 `rt/lowcmd`（同家族的 D1 MaxPro 官方有）
或 `/dev/shm/spline_shm`（D1 EDU 走這條），但**都還沒上實機驗證**。

→ **這不擋你。** task6 也是在部署路徑未定案的情況下先做完模擬的。
但請照 task6 README 的措辭紀律：**不要寫「完全沒有部署路徑」，也不要寫「已經有部署路徑」**，
寫「未定案，證據在 `task7/docs/D1Max_控制方式調查_2026-08-25.md` §5」。

**一件好消息**：D1 Max 的官方 SDK 有 `OnJointStateData` 回呼，
可直接讀 16 顆馬達的**角度／角速度／力矩**。這代表**觀測層的校準不必等底層寫入打通**，
拿高層 SDK 就能驗證 MJCF 跟實機對不對得上。task6 為了拿到同樣的東西花了好幾天做 SHM 偵察。

## 4. 模型資產

### 4.1 URDF（已在版控裡）

`task7/model/max.urdf` — 官方 `AgibotTech/Agibot_D1_Max` 的 `urdf/max_description/urdf/max.urdf`。

- ✅ 質量加總 **41.045 kg**，與規格書 41 kg 吻合 → 這份 URDF 的慣量資料可信
- ❌ **STL 網格沒收進版控**（`BASE_LINK.STL` 單檔 66 MB）。要用時從官方 repo 抓 `urdf/max_description/meshes/`
- ⚠️ **所有 `velocity` 限值都是 0**（沒填），轉 MJCF 必須自己補（見 4.3）
- ⚠️ **輪的 `effort=50`，但規格書寫 33 N·m**。保守取 33

### 4.2 ★★ 官方 MJCF 已經有了 —— 不用自己轉

`task7/model/zgws/zgws.xml` 是**智元官方的 D1 Max MuJoCo 模型**
（從 MATRiX 官方模擬器 v0.1.2 的 `base-0.1.2.tar.gz` 解出，逐字元未改）。
**已在 MuJoCo 3.10 載入通過**，並用它驗證過原廠站姿、質心、機身高度、輪半徑。

```bash
bash task7/model/zgws/fetch_assets.sh    # 先取回 54 MB 網格（未進版控）
# 之後直接載入 task7/model/zgws/scene_flat.xml（我們寫的乾淨平地場景）
```

**開工前請完整讀 `task7/model/zgws/SOURCE.md`**，它有：關節 qpos 位址表、
站姿驗證結果、官方 MJCF vs 官方 URDF 的質量落差、以及**直接用之前必須處理的三件事**。

先把那三件事列在這裡，因為它們直接影響你怎麼寫 CPG：

1. **致動器是純力矩 `<motor>`，沒有位置伺服、沒有 ctrlrange。**
   官方的 PD 由外部 `mc_ctrl` 提供。你要嘛加 `<position>` 致動器，
   要嘛在迴圈裡自己算 PD（task6 是後者）。增益用原廠那組（§6）。
   ⚠️ 沒有 ctrlrange 代表**「指令被靜默 clip」這個 task6 的經典症狀在這裡不會發生**，
   但關節限位仍會擋，所以 clip 診斷改成「IK 解出的角度有沒有超 `jnt_range`」。
2. **沒有 keyframe**，沒有現成初始姿。用驗過的 RL 預設姿（hip ±0.8 / knee ∓1.5）建一個。
3. **輪關節沒有 damping / frictionloss。** 實機輪馬達有靜摩擦，
   task6 是用實測掙脫門檻填的；這台還沒量過，先留空或給小值並註明是猜的。

### 4.3 機構參數表（校對 MJCF、或需要規格書數字時用）

**腿命名對應**（URDF 的 `F/R` = 前/後，`AR`/`BL` = 右/左，由 y 座標確認）：

| URDF | SDK 關節名 | 位置 |
|---|---|---|
| `FAR_*` | `fr1/2/3/4` | 右前 |
| `FBL_*` | `fl1/2/3/4` | 左前 |
| `RAR_*` | `br1/2/3/4` | 右後 |
| `RBL_*` | `bl1/2/3/4` | 左後 |

SDK 編號：`1`=hip_roll(abad)、`2`=hip_pitch、`3`=knee_pitch、`4`=foot(輪)。

| 關節 | 型別 | 軸 | 限位 (rad) | 扭矩 | 轉速上限 |
|---|---|---|---|---|---|
| ABAD | revolute | x | 右 −0.697~+0.523、**左 −0.523~+0.697** | 150 N·m | 190 RPM ≈ **19.9 rad/s** |
| HIP | revolute | y | ±2.443 (±140°) | 150 N·m | 同上 |
| KNEE | revolute | y | ±2.801 (±160°) | 150 N·m | 同上 |
| FOOT（輪） | **continuous** | y | ±3.14 | **33 N·m**（取規格書） | 1200 RPM ≈ **125.7 rad/s** |

- 髖位置 `x = ±0.272`、`y = ±0.065`；大腿 **0.26 m**、小腿 **0.28 m**、輪半徑 **0.09 m**
- 質量：BASE **20.25 kg**；每腿 ABAD 0.2696 + HIP 2.6525 + KNEE 1.5888 + FOOT 0.688 = **5.199 kg**
- 站立尺寸 930 × 480 × 585 mm

⚠️ **ABAD 左右限位是鏡像的**（右腿 −0.697~+0.523、左腿 −0.523~+0.697）。
task6 的 D1 EDU 是四腿同號，這裡不是。IK 出來的角度要逐腿檢查有沒有超限，
**不要只檢查一條腿就當四條都過**。

⚠️ **ABAD 行程只有 ±30°~40°**，跟 D1 EDU 一樣窄（Go2 是 ±60°）。
task6 因此把 `D_STEP_Y` 從 0.12 降到 0.09，這台要重算。

### 4.4 感測器安裝位置（相對 BASE 原點，m）

`IMU_ICM42688`（運控用）`(0, 0, 0.0362)`、`IMU_LUA300C`（車規級）`(0, 0, 0.0569)`。
⚠️ URDF 裡 `IMU_LUA300C_JOINT` 寫成 `0.00569`，**少一個零，以手冊的 56.9 mm 為準**。

### 5.1 `cpg_walk_d1.py` 裡三個「是方法、不是數值」的修正

這三個是 task6 花最多力氣才找到的，**在 D1 Max 上一樣會遇到，但數值要重掃**：

1. **`x_off`（足端前後基準偏移）** —— 質心不在四腳支撐中心時，前後腳離地量會差很多。
   task6 的 D1 EDU 質心偏後 17 mm，用 −40 ~ −55 mm 配平。
   **D1 Max 的質心偏移必須自己量**（MJCF 建好後靜態量四腳受力即可）。
   ⚠️ 這個值**隨步態與步頻而變，不是常數**；而且低步頻下它是**雙穩態不是連續配平**。
2. **`mu_y`（橫向擺幅）** —— 直線走路不需要橫擺，設成讓 `fy = 0` 的值（task6 是 1.5）。
   不歸零會造成側偏與左右不對稱。
3. **`g_c`（抬腳指令）** —— 前兩項修好後才有本錢加大。
   ⚠️ **調太大會讓 IK 解出的角度超出 ctrlrange 被靜默 clip**（task6 在 0.14 時 5.4% 指令被吃掉）。
   **一定要加一個「clip 比例」的診斷輸出**，否則你會看到步態變差卻找不到原因。

### 5.2 低步頻必須配 walk 步態（這個結論可能跨機型成立，但要重驗）

task6 實測：trot 在低步頻反而彈跳更大（兩腳支撐的空檔身體會下沉）。
解法是 walk 四拍步態把佔空比拉到 0.75~0.80，讓任一時刻三腳著地。
`duty_remap()` 那個函式（把相位重映射成指定佔空比）可以原樣搬。

**D1 Max 重一倍，下沉問題可能更嚴重，也可能因為關節扭矩大五倍而不明顯——要重測，別假設。**

## 6. 必須重新決定的參數清單

**★ 先讀 `task7/docs/D1Max_原廠運控參數_MATRiX解包_2026-08-25.md`。**
我們從 MATRiX 官方發布包解出了**原廠運控實際在跑的設定檔**，
下表一半以上的項目因此已經有答案，不用自己從零掃。
（那批數字的可信度有獨立交叉驗證：同一批檔案裡 D1 EDU 那份的增益，
與 task6 在實機量到的原廠值逐項吻合。）

| 參數 | task6 的值 | **D1 Max** |
|---|---|---|
| `KP` | 80（三個腿關節共用） | ★ **ABAD 60 / HIP 120 / KNEE 120**（原廠 RL 用；**不是共用一個值**） |
| `KD` | 1.0 | ★ **1.0**（腿）；輪 **Kp 60 / Kd 0.5** |
| `TAU_MAX` | 28 N·m | **150**（腿）/ **33**（輪） |
| `WHEEL_RADIUS` | 0.0710 | **0.090** |
| `HOME3` | `[0, 1.05, −2.00]` 四腿共用 | ★ **前後反號，不能四腿共用**：站姿 hip `[0.6, 0.6, −0.6, −0.6]`、knee `[−1.2, −1.2, 1.2, 1.2]`（腿序 FR/FL/RR/RL）。RL 預設姿是 hip ±0.8 / knee ∓1.5 |
| `NOMINAL_HEIGHT` | 0.2695 | ★ 起點 **0.48 m**（原廠 `body_height`），再扣位置伺服靜態撓度 |
| `G_C`（抬腳高度） | 0.08 / 步態用 0.12 | ★ 起點 **0.10 m**（原廠 `leg_height`），再掃並監控 clip 比例 |
| `D_STEP` / `D_STEP_Y` | 0.12 / 0.09 | ❌ 自己算。連桿 0.26+0.28 比 D1 EDU 長，ABAD 行程要重查 |
| `OMEGA_MAX` | 2.5 | ❌ 自己掃 |
| `x_off` | −0.040 ~ −0.055 | ❌ 自己掃（先量質心偏移），原廠設定檔沒有對應項 |
| `CTRL_DT` | 0.02（50 Hz） | 原廠運控是 **500 Hz**（`controller_dt = 0.002`）。你出指令用 50 Hz 沒問題，但別假設底層也是 50 |
| `LEGS` 腿序 | `(FL, FR, RL, RR)` | ★ 原廠是 **`FR, FL, RR, RL`**（`zg_wheels-motion_config.yaml` 裡寫死）。**建議直接跟它一致**，省掉一層重排 |
| 關節速度上限 | — | 設定檔寫 24.0 rad/s、規格書 190 RPM ≈ 19.9。**不一致，保守取 19.9** |
| `OBS_DIM` | 69 | 只有做 RL 才需要，純 CPG 用不到 |

### ⚠️⚠️ 這裡面最會咬人的一項：站姿是前後鏡像的

D1 EDU 四腿同號（`hip_stand_pos = [0.8, 0.8, 0.8, 0.8]`），
**D1 Max 前兩腿與後兩腿反號**（`[0.6, 0.6, −0.6, −0.6]`）—— 站姿是 **X 型**。

→ **「四條腿套同一組 IK 公式 / 同一個 HOME3」的寫法在這台會錯。**
task6 的 `d1_model.HOME3` 是四腿共用一個三元組，照抄會做出一隻前後腿方向相反的怪東西。
MJCF 建好後**第一件事就是把原廠站姿角度餵進去驗證**：四條腿撐得住、機身高度 ≈ 0.48 m。

## 7. 從 task6 帶過來、會咬人的坑（這些是方法，跨機型有效）

**這五件事請務必當真，每一件 task6 都實際踩過：**

1. **量測指標會騙人。** `task6/docs/HANDOFF_CPG-RL_2026-08-12.md` **§4「⚠️ 會騙人的指標」**
   列了踩過的坑。做步態品質評估前**先讀那一節**（§2 有各版本的實測對照表可當格式範本）。
2. **相位差要用圓形統計。** ±180° 的包裹會讓標準差虛胖，看起來像相位沒鎖定其實鎖得很好。
3. **trot 的理論前進量每週期有「兩個」站立相**，算速度時漏掉會差一倍。
4. **靜默失效比報錯可怕。** `mj_name2id` 找不到會回 −1，而 Python 的 `-1` 索引會**靜默拿到最後一個元素**
   （拿到 RR 的資料卻以為是 FL）。task6 的做法是每次查名稱都 `assert gid >= 0`，照抄。
5. **常數要鎖成唯讀。** `HOME3[0] = 99` 在 numpy 上會成功且不報錯，然後全域擴散。
   task6 用 `arr.flags.writeable = False` 鎖住，照抄。

另外兩個**校正層**的教訓（做到 sim2real 才會用到，但先知道比較好）：

6. **不要用站姿反推 offset。** 「假設站姿 ≈ MJCF home」會做出一組**自洽但錯誤**的映射——
   所有檢查都通過，但實機一動就錯。
7. **「事後重設 qpos」不等於機身固定。** task6 曾經以為空中模擬的機身被固定住了，
   實際上關節完全沒有重力，整個空中步態結果作廢重來（commit `c8e03b3`）。
   要固定機身就在 MJCF 裡固定，不要在迴圈裡改 qpos。

細節見記憶檔 `d1-edu-calibration-lessons`，或 `task6/docs/` 對應文件。

## 8. 建議的做法順序

1. **取回網格、載入官方 MJCF**（`fetch_assets.sh` → `scene_flat.xml`）。
   讀 `task7/model/zgws/SOURCE.md`。**不用做 URDF→MJCF 轉檔了。**
2. **補 MJCF 缺的三樣**：位置伺服（或迴圈內 PD）、初始姿 keyframe、輪關節摩擦。
   增益用原廠那組（ABAD 60 / HIP 120 / KNEE 120 / Kd 1.0、輪 60/0.5）。
3. **靜態驗證（動態落地版）**：讓它在 `scene_flat.xml` 上真的站起來並收斂，
   量機身高度（應 ≈ 0.49 m）、四輪受力分佈、跑起來之後的實際質心偏移。
   ⚠️ 我做的是**正向運動學**的靜態檢查（質心偏移 −0.6 mm），
   **不是落地模擬**，位置伺服的靜態撓度與接觸都還沒算進去。
4. **IK + 單腿驗證**：足端目標 → 關節角，逐腿檢查有沒有超 `jnt_range`
   （左右 ABAD 限位不同、前後 HIP 限位也不同！）。
5. **CPG 接上去**：先 trot 跑起來，再做 `duty_remap` 的 walk。
6. **掃參數**：`x_off` → `mu_y` → `g_c`，順序照 §5.1，每一步都輸出超限比例。
   ⚠️ `x_off` 可能接近 0（這台質心幾乎沒偏），但**別直接假設 0**，還是要掃。
7. **出影片 + 量化表**（四腿離地、週期俯仰、垂直彈跳、支撐腳數、前進速度），
   格式抄 `cpg_walk_d1.py` 的 §3 表格。
