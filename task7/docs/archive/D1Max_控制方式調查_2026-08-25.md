# 智元 D1 Max（zsm-1w）控制方式調查

- 調查日期：2026-08-25
- 對象：智元 AgiBot **D1 Max** 輪足四足機器狗，SDK 代號 `zsm-1w`
- 目的：搞清楚「這隻狗能怎麼控制」——高層 SDK 能做到哪、底層能不能寫馬達
- 方法：全部是**文件與二進位檔層級的查證**，尚未上實機。標示 ✅ 的是有證據的事實，⚠️ 的是推論。

---

## 0. 一句話結論

**官方 SDK（`RobotSDK` / `librobot_sdk.so`）只開放高層控制**：站立、趴下、匍匐、爬高台、
速度指令 `Move(vx, vy, yaw)`、姿態、燈光。**讀是全開的**（IMU / 運動狀態 / **關節角度、角速度、力矩**
/ 電池 / 光達 / 超音波 / RTK / 影像），**寫只到「速度百分比」這一層**——送不了關節角度或力矩。
這點我用 `nm -D` 對 `librobot_sdk.so.0.2.1` 驗過：269 個導出符號，全部是 `robot_sdk::SDKClient::*`，
**零個底層符號、`strings` 也搜不到 `lowcmd` / `spline` / `/dev/shm`**。

但是——**同家族的 D1 MaxPro 官方直接開放了 ROS2 底層介面 `rt/lowcmd` / `rt/lowstate`**
（可下 `q_des` / `kp` / `kd` / `tau_ff`，正是部署 RL policy 需要的東西）。D1 Max 的文件沒有列這個介面，
但 D1 Max 本身就跑 ROS2 humble + zenoh，且與 D1 EDU 共用 `robot-launch` 行程管理工具。
⚠️ **所以「D1 Max 有沒有底層」是一個上機跑 `ros2 topic list` 就能一秒回答的問題，
不要再從文件推論。**（第 6 節有唯讀偵察腳本。）

## 1. 先把三台狗分清楚，不然會拿錯 SDK

智元／zsibot 至少有三條產品線，GitHub 上是三個不同的 repo、三套不相容的 SDK。**代號比產品名可靠。**

| 產品 | SDK 代號 | repo | SDK 命名空間 | 底層控制 |
|---|---|---|---|---|
| D1 EDU（點足 / 輪足） | `zsl-1` / `zsl-1w` | `zsibot/genisom_L1_sdk` | `mc_sdk::zsl_1w::HighLevel` | 點足有 UDP LowLevel；輪足**無** |
| **D1 Max ← 本次對象** | **`zsm-1w`** | **`AgibotTech/Agibot_D1_Max`** | **`robot_sdk::SDKClient`** | **SDK 無；ROS2 待驗** |
| D1 MaxPro | — | `AgibotTech/Agibot_D1_MaxPro` | `high_level_remote_tcp_client` | ✅ **有**：ROS2 `rt/lowcmd` |

**⚠️ 最容易踩的坑：D1 Max 跟 D1 EDU 的 SDK 完全不共用。** 不是換個機型參數就好——
命名空間、傳輸協定、函式名、資料結構全部不同。task6 累積的 `mc_sdk` 相關程式碼在這台上一行都用不到。
（唯一可能共用的是 `/dev/shm` 那條路，見第 5 節。）

D1 Max 的 SDK 在 GitHub 上有兩個一模一樣的鏡像：
- `AgibotTech/Agibot_D1_Max` — 附**完整中文手冊**（`docs/source/*.md`）與 **URDF**，這份最有用
- `zsibot/genisom_robot_sdk` — 只有 SDK 本體，但**版本較新（0.2.1，含更多 API）**，另附原始協定 PDF

✅ 兩邊的 `include/robot_sdk/*.hpp` 是同一套。建議：**手冊看 AgibotTech 那份，程式庫用 zsibot 那份。**

## 3. 系統架構與連線方式

### 3.1 雙板架構（這是跟 D1 EDU 最大的結構差異）

```
┌─────────────────────────────────────────────┐
│ RK3588        運動控制 + 系統監控             │  ← 官方明文：「勿在此板開發應用程式」
│               ssh robot@192.168.234.1 (wifi)│
│                   robot@192.168.168.168 (有線)│
│               密碼 bot                       │
├─────────────────────────────────────────────┤
│ Orin NX 16GB  建圖 / 定位 / 導航 / 使用者應用  │  ← 官方指定的開發板
│               ssh robot@192.168.168.100      │
│               密碼 1                         │
│               ROS2 humble + zenoh, DOMAIN=24 │
└─────────────────────────────────────────────┘
```

✅ **運控在 RK3588、應用在 NX。** 這代表如果真要做底層控制（1kHz 級），
跑在 NX 上要跨板通訊，延遲與抖動必須實測，不能假設跟 D1 EDU 的板內 SHM 一樣好。

### 3.2 連線

| 方式 | 設定 |
|---|---|
| WiFi | SSID `XG2WIFI_xxxxxx`，**密碼 `12345678`**（✅ 官方文件明載，不像 D1 EDU 要跟售後要） |
| 有線 | 網線接機身拓展網口；PC 網口設 `192.168.168.x`，**不可用 .168 與 .100**（那是狗的兩塊板） |
| SDK | UDP（0.1.1 起預設從 WebSocket 改為 UDP）→ `192.168.234.1:8082` |
| 影像 | RTSP `rtsp://192.168.234.1:8554/front`、`/back` |
| 內部光達 | 前 `192.168.1.102`、後 `192.168.2.102`（獨立網段，別跟主網段搞混） |

⚠️ **注意 `192.168.168.100` 在 D1 Max 上是「Orin NX 的位址」。**
task6 的 D1 EDU 連線 SOP 裡，`192.168.168.100` 是**我們電腦自己的靜態 IP**
（NetworkManager profile `dog-direct`）。**直接沿用會撞位址。**
接 D1 Max 時電腦要改成 `192.168.168.x` 的其他值（例如 .50）。

### 3.3 行程管理

RK 與 NX 都用 `robot-launch` 管行程（**與 D1 EDU 相同的工具**）：
```
robot-launch help              # 說明
robot-launch egg <id>          # 查節點狀態
robot-launch start|stop <id>   # 起停節點
```
日誌：本次開機 `/home/robot/robot_launch_log`；最近 6 次 `/userdata/log/`。

✅ 共用 `robot-launch` 是「兩台狗的底層軟體堆疊同源」的證據，
也是我認為 `/spline_shm` 值得上機找一找的主要理由。

## 4. 路線 A：官方 SDK 高層控制（可立即使用）

### 4.1 環境需求

- Ubuntu **22.04**、CMake 3.8+、GCC 11+、**Boost 1.74+**、C++
- 庫已預編好：`lib/x86_64/` 與 `lib/aarch64/`，所以**可以在自己的電腦上跑，也可以放到 NX 上跑**
- ⚠️ **SDK 版本必須配狗內韌體版本**。查法：
  ```
  ssh robot@192.168.234.1   'cat /opt/release/version.yaml'   # RK 韌體版本
  ssh robot@192.168.168.100 'cat /opt/release/version.yaml'   # NX 韌體版本
  ```
  對照 repo README 的相容表；不合就找售後要對應版本。**版本不合的症狀是錯誤碼 `10001 ProtocolMismatch`。**

### 4.2 能「寫」的指令（`robot_sdk::SDKClient`）

以下是我從 `librobot_sdk.so.0.2.1` 的導出符號實際列出來的 ✅，比手冊還全
（手冊沒寫到 `PosControl` / `PosMove` / `SkWalk` / `Sand` / `Stair` / `CrawlWalk` / `BalanceStandUp` 等）：

**姿態／狀態**
`StandUp` `BalanceStandUp` `LieDown` `Crawl` `CrawlWalk` `Climb`（爬高台）`Stair`（登階）
`Slim`（瘦身穿窄縫）`Sand`（沙地姿態）`DSB`（過擋鼠板）`Gait`（步態）`SkWalk`（同膝行走）
`Locked`（鎖定，各關節保持現位）`ReverseHeadTail`（調轉頭尾）

**移動**
- `Move(left_right, forward_back, yaw)` — **單位是百分比 [-1, 1]，不是 m/s**，實際速度由 `SetSpeed` 的等級決定
- `Turn(direction)` 原地翻滾、`ControlHead(lr, ud)` 探頭、`HighLowStance(stance)` 高低站姿（**僅原地模式有效**）
- `PosControl` / `PosMove` — 位置控制（x,y,z,roll,pitch,yaw），手冊未詳述，**待上機摸**

**模式與速度**
- `SetMode(mode)` — `1` 通用 / `2` 原地 / `3` 登階
- `SetSpeed(level)` — `1` 低 / `2` 中 / `3` 高

| 速度等級 | forward_back 全幅 | left_right | yaw |
|---|---|---|---|
| 低速 | ±1.0 m/s | ±0.5 m/s | ±1.5 rad/s |
| 中速 | ±2.0 m/s | ±0.5 m/s（前後 >1 m/s 時鎖 0） | ±1.5 → >1m/s 時 ±1.0 rad/s |
| 高速 | ±3.0 m/s | 同上 | 前後 >2 m/s 時降到 ±0.5 rad/s |

⚠️ 規格書寫最大 6 m/s，但 SDK 高速檔只給到 3 m/s。**6 m/s 應該不是 SDK 能開出來的。**

**⚠️ `Move` 指令只維持 1 秒**，要持續走必須週期性重送（跟 D1 EDU 的 50 Hz 高層一樣的心跳邏輯）。

**安全／控制權／周邊**
`SoftEmergencyStop(on)` `TakeControl` `ReleaseControl` `SwitchIdleState` `SwitchRemoteState`
`ObstacleAvoidance` `FrontLight` `BackLight` `AutoModeLight` `SetLedCommand` `SetPeriphPower`
`TakePhoto` `UpdateCameraBitrate` `StartRechargeTask` / `StopRechargeTask`（自主回充，選配）

### 4.3 能「讀」的資料（`IDataCallback`）

| 回呼 | 內容 | 頻率 |
|---|---|---|
| `OnImuData` | acc / gyro / **四元數（欄位是 `quat_x,y,z,w`）** | `SetImuConfig(freq)`，0–100 Hz，**預設關閉** |
| `OnMcData` | **四元數 `quat[4]` 註解寫 `[w,x,y,z]`**、世界座標位置/速度/角速度、機體速度/角速度、ns 時戳 | `SetMcConfig(true)` → 50 Hz，預設關閉 |
| **`OnJointStateData`** | **`names` / `positions` / `velocities` / `efforts`** | `SetJointStateConfig(true)`，v0.1.0 起 |
| `OnSpeedData` | vx / vy / yaw | `SetSpeedReportConfig(on, 1–50 Hz)` |
| `OnRobotStateData` | 運動狀態、機器狀態、電池 ×2、**每關節溫度 map**、控制來源、軟/硬急停狀態 | 主動 1 Hz |
| `OnFaultData` | 故障碼（馬達失能/編碼器/離線/過壓/過熱/CAN/IMU…） | 發生時 |
| `OnControlLost` / `OnControlAvailable` | 控制權被搶／可用 | 事件 |

**⚠️⚠️ 四元數順序有兩種寫法、而且互相矛盾**：`ImuData` 的欄位名是 `quat_x, quat_y, quat_z, quat_w`（xyzw），
`MotionData` 的註解卻寫 `Quaternion [w, x, y, z]`。**兩個都不能信，上機必須自己驗**——
這正是 task6 在 D1 EDU 的 `imu_shm` 上踩過的坑（記錯順序解出 roll = +125°）。
**驗法照舊：狗平趴在地，roll/pitch 必須 ≈ 0。**

**★ `OnJointStateData` 是這次調查最有價值的發現之一。**
它給了 16 顆馬達的角度／角速度／力矩，代表**就算底層寫不進去，
我們仍然可以拿實機真值去校準 MJCF、驗證 sim2real 的觀測層**——這是 task6 花了好幾天用
`/spline_shm` 唯讀偵察才換到的東西，這台用官方 API 就有。

### 4.4 狀態機與控制權（會咬人的地方）

- ✅ **指令必須照狀態機順序下，否則「可能造成機器摔倒、故障或不響應」**（官方原話）。
  站立完成後會依當前模式自動切到通用／原地／登階狀態。鎖定狀態下切到任何其他狀態即解鎖。
- ✅ **控制權是不對稱的**：
  - APP（遙控器）**可以**搶走 SDK 的控制權
  - SDK **不能**搶走 APP 的控制權 → 錯誤碼 `10002 ControlledDenial`
  - 所以標準流程是：**先確認遙控器 APP 沒連著 → SDK `TakeControl()` → 才下指令**
- ⚠️ **想在 SDK 控制期間保留遙控器急停能力，必須在 SDK 取得控制權後「點開 APP」**，
  之後才能用遙控器右上角紅色急停鈕。**這步漏掉 = SDK 跑飛時沒有遙控器急停。**
- ✅ 官方警告：「執行 SDK 時請保證系統有足夠資源，否則可能出現**運動控制模組失效**」。
  → 別在 RK3588 上跑重的東西（呼應「勿在此板開發應用程式」）。

### 4.5 安全機制

| 類型 | 觸發 | 效果 |
|---|---|---|
| 硬急停 | 機身急停按鈕 | 緩慢著地、紅燈；旋開後自動恢復 |
| 軟急停 | 遙控器 or `SoftEmergencyStop(true)` | 立即停車，**不再響應任何控制指令**，保持當前姿態 |
| 內部保護（自動） | 遙控斷連／電量 <10%／關節故障／IMU 通訊中斷 | 自動停車並緩慢著地 |

## 5. 路線 B / C：底層控制（未驗證，這是下一步的主戰場）

### 5.1 證據一：SDK 裡確定沒有

```bash
nm -D --defined-only librobot_sdk.so.0.2.1 | c++filt | grep -c "robot_sdk::SDKClient::"
# → 269 個導出符號，全部是 SDKClient::*
strings librobot_sdk.so.0.2.1 | grep -iE "lowcmd|lowstate|spline|/dev/shm|tau_ff|torque"
# → 一個都沒有
```
✅ 跟 D1 EDU 輪足的結論一樣：**不是漏放標頭檔，是庫裡真的沒有。**
但也跟 D1 EDU 一樣——**這管不到 SDK 以外的路。**

### 5.2 證據二：同家族的 MaxPro 有，而且長這樣

D1 MaxPro 官方文件 `4.2 底層電機控制接口`：**ROS2 topic**

- **下行 `rt/lowcmd`**
  ```
  float32[4] q_des_abad / q_des_hip / q_des_knee     # 目標角度
  float32[4] qd_des_abad / qd_des_hip / qd_des_knee  # 目標角速度
  float32[4] kp_abad / kp_hip / kp_knee              # P 增益
  float32[4] kd_abad / kd_hip / kd_knee              # D 增益
  float32[4] tau_abad_ff / tau_hip_ff / tau_knee_ff  # 前饋力矩
  int32[4]   flags                                    # 每條腿控制模式
  ```
- **上行 `rt/lowstate`**：IMU（角速度／加速度／四元數／`imu_is_valid`／`packet_id`）
  + 12 顆馬達的 `q` / `qd` / `tau` + `flags` + `spi_driver_status` + 異常等級

這正是 Unitree 風格的 PD + 前饋介面，**部署 CPG-RL policy 需要的全部原語都在這裡**。
MaxPro 的高層還額外有「**強化學習模式**及**零力矩模式**」。

⚠️ 注意 `rt/lowcmd` **只涵蓋 abad/hip/knee 共 12 顆，沒有輪子**。
若 D1 Max 也是這個形狀，輪子要另外找介面（或維持高層控制）。

### 5.3 D1 Max 上要驗的三件事

| # | 假設 | 驗法（唯讀） | 若成立的意義 |
|---|---|---|---|
| B | 存在 `rt/lowcmd` / `rt/lowstate` | `ros2 topic list \| grep -i low` | **最佳結果**，直接照 MaxPro 的結構寫 |
| C | 存在 `/dev/shm/spline_shm` | `ls -l /dev/shm/`（RK3588 上） | 可沿用 task6 的 `shm_common.py` 骨架 |
| D | 都沒有 | — | 只能走高層 SDK，或跟原廠要底層權限 |

⚠️ **B 要在哪塊板上找是個問題。** 運控在 RK3588，但文件教使用者 `ros2 topic echo` 是登入 NX。
所以**兩塊板都要跑一次 `ros2 topic list`**；也可能運控用的是 RK 板內的 DDS，NX 上看不到。

## 7. 模擬模型資產

`AgibotTech/Agibot_D1_Max` 的 `urdf/max_description/` 有完整 URDF + STL。
**URDF 已抓進 `task7/model/max.urdf`**（36 KB）；STL 網格沒抓（`BASE_LINK.STL` 單檔就 66 MB）。

### 7.1 關節表（✅ 從 URDF 實際解析）

命名：`F`/`R` = 前/後，`AR`/`BL` 對應右/左（由 y 座標確認：`y = -0.065` 右、`y = +0.065` 左）

| URDF | SDK 名 | 位置 |
|---|---|---|
| `FAR_*` | `fr1/2/3/4` | 右前 |
| `FBL_*` | `fl1/2/3/4` | 左前 |
| `RAR_*` | `br1/2/3/4` | 右後 |
| `RBL_*` | `bl1/2/3/4` | 左後 |

SDK 的關節編號規則：`1` = hip_roll(abad)、`2` = hip_pitch、`3` = knee_pitch、`4` = foot(輪)。
例：`fr1_hip_roll`、`bl3_knee_pitch`。

| 關節 | 型別 | 軸 | 限位 (rad) | effort | 備註 |
|---|---|---|---|---|---|
| ABAD | revolute | `1 0 0` (x) | 右腿 **-0.697 ~ +0.523**、左腿 **-0.523 ~ +0.697** | 150 | **左右鏡像** |
| HIP | revolute | `0 1 0` (y) | ±2.443 (±140°) | 150 | |
| KNEE | revolute | `0 1 0` (y) | ±2.801 (±160°) | 150 | |
| FOOT（輪） | **continuous** | `0 1 0` (y) | ±3.14 | **50** | ⚠️ 與規格書的 33 N·m 不符 |

幾何：髖 x = ±0.272、y = ±0.065；大腿 0.26 m、小腿 0.28 m；輪半徑 9 cm。

質量（✅ URDF 加總 = **41.045 kg**，與規格書 41 kg 吻合，這份 URDF 的慣量資料可信）：
BASE 20.25、每腿 ABAD 0.2696 + HIP 2.6525 + KNEE 1.5888 + FOOT 0.688 = 5.199 kg，四腿 20.79 kg。

**⚠️ 兩個 URDF 的坑：**
1. **所有 `velocity` 限值都是 0**，等於沒填。轉 MJCF 時要用規格書的值：
   腿 190 RPM ≈ **19.9 rad/s**、輪 1200 RPM ≈ **125.7 rad/s**。
2. **輪的 effort 50 vs 規格書 33 N·m 不一致**，保守取 33。

### 7.2 感測器安裝位置（相對 BASE 原點，m）

`IMU_ICM42688`（運控用）`(0, 0, 0.0362)`；`IMU_LUA300C`（車規級）`(0, 0, 0.0569)`；
前光達 `(0.4043, 0, -0.0377)`、後 `(-0.4043, 0, -0.0377)`；
前相機 `(0.4123, 0, 0.0378)`、後 `(-0.4123, 0, 0.0378)`；
超音波 `(0.1792, ∓0.1002, 0.05)`。

⚠️ URDF 裡 `IMU_LUA300C_JOINT` 的 `xyz` 寫成 `0.00569`，但手冊表格寫 56.9 mm = `0.0569`。
**URDF 少了一個零，以手冊為準。**

### 7.3 ROS2 感測 topic（✅ 官方文件列出）

`/front_lidar`、`/rear_lidar`（PointCloud2, 10 Hz, best_effort）、
`/front_lidar/imu`、`/rear_lidar/imu`、`/imu_driver/imu_central`（`sensor_msgs/Imu`）、
`/uss_driver/uss_left/range`、`/uss_driver/uss_right/range`（10 Hz）、`/rtk_pvh`。

從 PC 連 ROS2 graph 需要：Ubuntu 22.04 + ROS2 humble + `ros-humble-rmw-zenoh-cpp`，

`DEFAULT_RMW_ZENOH_ROUTER_CONFIG.json5` 的 `connect/endpoints` 指到 `tcp/192.168.168.100:7447`。

## 8. 跟 task6（D1 EDU）比，哪些經驗能用、哪些不能

| task6 的經驗 | 能不能用在 D1 Max |
|---|---|
| `mc_sdk` 相關的所有程式碼 | ❌ 完全不同的 SDK，一行都不能用 |
| kp=20 / kd=0.7、力矩 5 N·m 保護門檻 | ❌ **這台是 41 kg / 150 N·m，量級全錯** |
| 電腦端 `192.168.168.100` 靜態 IP | ❌ **會撞到狗的 Orin NX**，要改 |
| 「四元數順序必須實測」的教訓 | ✅ 完全適用，而且這台文件自相矛盾，更該驗 |
| 「編碼器零點/正負跟 URDF 對不上，要補校正層」 | ✅ 適用，`OnJointStateData` 是驗這件事的好工具 |
| 「先讀後寫、分階段、全程吊掛」的方法論 | ✅ 適用，41 kg 更該嚴格執行 |
| `robot-launch` 行程管理、`/dev/shm` 直寫的思路 | ⚠️ 同源工具，值得找，但未驗證 |
| `pgrep -f` 會匹配到自己的 shell 這種坑 | ✅ 適用 |
| 圓形統計量相位差、trot 每週期兩個站立相 | ✅ 純方法，跨機型適用 |
