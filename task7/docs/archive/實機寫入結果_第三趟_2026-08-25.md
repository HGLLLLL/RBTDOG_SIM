## 2. M1 —— 寫得進去，但被清零

```
共寫入 600 輪（200 Hz × 3 秒）
mc_ctrl 狀態 S → T（凍結成功）→ S（解凍成功）

寫入後讀回相符：0/16          ← ⚠️
全機最大速度 0.0030 rad/s
全機最大力矩 0.0824 N·m       ← ✅ 零出力達成
```

**關鍵細節**：讀回的 `p_des` 不是原本的 offset、也不是我們寫的實測角度，
而是**整齊的 `0.0000`**。有第三方把指令區清成零了。

### 根因：base+0 是心跳時戳，不是我先前以為的容器欄位

回頭比對第二趟的兩份快照（間隔 2 秒）：

```
joint_cmd    base+0:  1184236 → 1186664   (+2428，≈1 kHz)
joint_state  base+0:  1186768 → 1188865   (+2097，同一個時鐘，只是晚約 2 秒取樣)
```

- **16 筆記錄的值完全相同** → 是整幀共用的時戳，不是每關節的欄位
- 值 `0x1211EC` 大於 1 MiB 的區段大小 → 不是段內指標
- 遞增速率 ≈ 1 kHz（重測時實測為恰好 1000/s），與 `controller_manager update_rate` 吻合

⚠️ **我在第二趟把它寫成「容器內部欄位（每筆相同）」，那是錯的。**
文件與 `shm_decode.py` 都已更正。

### 事情的經過

1. `SIGSTOP` 凍結 `mc_ctrl` → 這個心跳**停住**
2. `joint_shm_controller` 依 `joint_cmd_timeout: 500 ms` 判定指令過期
3. 逾時處置：**把指令區清成 0**
4. 我們持續寫 5 個浮點數，但時戳不動 → 一直被判過期 → 一直被清

**所以「0/16 相符」不代表寫不進去。** 三個佐證說明寫入本身沒問題：

- `sudo` 下 `mmap` 寫入沒有被拒絕（沒有例外、沒有 EACCES）
- 力矩 0.0824 N·m 全程接近零 → 沒有失控，安全設計有效
- 原廠的逾時保護**確實會動作**，而且動作方向是安全的（清零而非維持舊指令）

這其實是個好消息：**逾時保護是真的在保護我們。**

## 3. 修法

`shm_io.py` 新增 `read_tick()` / `write_tick()`，M1 每一輪改成：

```
寫 16 顆的 5 個浮點數（payload）
  ↓
把 joint_state 當下的時戳抄進 joint_cmd 的 16 筆記錄   ← 新增
```

**順序不能反**：時戳等同「這幀備妥了」的旗標，一定要 payload 寫完才寫。

用 `joint_state` 的時戳而不是自己遞增，理由是：
- 它由活著的 `zsi_actuator_driver` 維護，永遠是新的
- 已證實與 `joint_cmd` 共用同一個時鐘
- 不必猜這個時戳的單位與原點

已用實機快照在本機驗證：`write_tick()` 會把 16 筆都寫到，且**不會破壞關節名稱結構**。
