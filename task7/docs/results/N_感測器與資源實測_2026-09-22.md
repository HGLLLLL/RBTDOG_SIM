## 1.3　資源使用情形

### 靜態規格（實機讀取）

| | RK3588（運控板） | Orin NX（應用板） |
|---|---|---|
| 板卡 | Firefly AIO-3588SJD4 HDMI(Linux) | NVIDIA Jetson Orin NX Engineering Reference Developer Kit |
| CPU | 8 核：`policy0` cpu0-3 **1.8 GHz**、`policy4` cpu4-5 與 `policy6` cpu6-7 **2.4 GHz** | 8×A78AE **1.984 GHz**（兩個 policy，同頻） |
| governor | `performance`（全核） | `schedutil` |
| RAM | **7916 MB** | **15656 MB** |
| swap | 0 | 7828 MB |
| 核心隔離 | `isolcpus=7`、`nohz_full=7` | 無 |
| OS / 韌體 | Ubuntu 22.04.5、kernel 5.10.160-**rt78-preempt**、`0.1.7` | Ubuntu 22.04.5、JetPack **R36.4.7**、`0.3.6` |
| 電源模式 | — | **MAXN** |

⚠️ **勘誤**：舊文件寫 RK 的 A76 是 2.4 GHz、A55 是 1.8 GHz，方向對，
但 `lscpu` 的 `Model name` 只報 **Cortex-A55**（只反映第一個 cluster），
`CPU max MHz` 也只有 1800 —— 引用時要用 `cpufreq` 的 per-policy 值，不要用 `lscpu` 那兩欄。

### 使用情形

| 板 | 情境 | 整體 CPU | 最忙的核 | 記憶體 | GPU | 最高溫 |
|---|---|---|---|---|---|---|
| RK3588 | 待機 31 s | **26.1%** | cpu6 59.4% | 1615 / 7916 MB（20%） | Mali 0% | 43.5 °C |
| RK3588 | 走路 41 s | **26.1%** | cpu6 61.1% | 1636 / 7916 MB（21%） | Mali 0% | 44.4 °C |
| Orin NX | 待機 30 s | **70.4%** | cpu0 78.5% | 7586 / 15656 MB（48%） | GR3D 平均 12%、峰 99% | 44.7 °C |
| Orin NX | 走路 40 s | **72.0%** | cpu0 79.1% | 7679 / 15656 MB（49%） | GR3D 平均 29%、峰 99% | 44.7 °C |

**四個要記住的結論**

1. **RK 很閒、NX 很滿。** 運控板整體 26%、記憶體只用兩成；應用板八顆核平均 70%、
   loadavg 13.6（8 核）已經超賣。**要塞自己的東西，空間在 RK 不在 NX。**
2. **走路對兩塊板幾乎沒有影響**（RK 26.1 → 26.1%、NX 70.4 → 72.0%）。
   原因是最大戶都跟走路無關：RK 是影像編碼、NX 是 SLAM 與定位，一直在跑。
   真正隨走路變的是 `mc_ctrl`（5.8% → **11.0%**，翻倍）與 NX 的 GPU（12% → 29%）。
3. **RK 的 cpu6 是瓶頸核（60%）**，因為所有 UART 中斷（`irq/114-ttyS3`、`116-ttyS5`、
   `118-ttyS9`）都綁在 cpu6。自己的推論程式要避開 cpu6。
4. **★ 核心隔離的 cpu7 上跑的是 `robot_hal_node/HwLoop`（綁定 `cpus=7`、16.2%）**，
   不是 `mc_ctrl`。`mc_ctrl` 整個行程綁 **0-6**。
   這推翻了我們原本「cpu7 給運控獨占」的說法 —— 精確的說法是
   **cpu7 給 HAL 的硬體迴圈獨占**，`mc_ctrl` 和一般行程搶 0-6。
   行程層級的 `Cpus_allowed_list` 看不出這件事，要看 `task/*/status`。

## 7.1　感測器種類與數量

topic 分兩個 DOMAIN：運控在 RK（`ROS_DOMAIN_ID=66`、56 個 topic），
感知導航在 NX（`=24`）。影像 topic 由 `bridge_image_topics_66` 橋到 RK 那側。

| 種類 | 數量與證據 | 實測頻率 |
|---|---|---|
| 光達 | `/front_lidar`、`/rear_lidar` 各 1，發布者 `rslidar_sdk` | 前 **10.022 Hz** |
| 光達自帶 IMU | `/front_lidar/imu`、`/rear_lidar/imu` | 前 **200.087 Hz** |
| 機身 IMU | `/imu_driver/imu_central`（NX）、`/imu_shm_publisher/imu_central`（RK） | **200.345 / 199.994 Hz** |
| 相機 | `/front_camera/image_compressed`、`/rear_camera/image_compressed` | **9.785 / 10.003 Hz** |
| 超音波 | `/uss_driver/uss_{left,right}/range` ×2 | 未量到 |
| UWB | `/uwb`、`/uwb_point` | 未量到 |
| RTK / GNSS | `/rtk_pvh`、`/uni_rtk_pvh`、`/gnss/data`、`/gps/rtk` | 未量到；`gpsd -s 115200 -n -P NMEA /dev/ttyS4 /dev/pps0` 在 RK 上跑，**有 PPS** |
| 2D 掃描 | `/laser_scan`（`LaserScan`，應該是點雲壓成的） | **4.547 Hz** |
| 電池 | `/battery_controller/battery{1,2,_all}` | **1.000 Hz** ×3 |
| 關節感測 | `/joint_shm_controller/joint_sensor`（含每關節溫度／電壓／error） | 之前已驗 |

`/gps/rtk` 與 `/gnss/data` 的**發布者數是 0** —— topic 在、沒人發。室內沒定位是合理的，
但要寫進報告得再確認是室內收不到訊號，還是驅動沒起來。

**周邊裝置**：RK 有 CH9344 USB 多序列埠橋（`usb_ch9344`）與 Realtek 藍牙；
NX 有兩張 CH397 USB 10/100 網卡（就是兩顆光達各一條）＋ CH9344 多序列埠。

## 7.4　LiDAR 等其他感測器

### 前光達（`/front_lidar`，一筆 `PointCloud2` 實測）

| 量 | 值 |
|---|---|
| 頻率 | **10.022 Hz** |
| 結構 | `height=900`、`width=96` 的**有序點雲** → **96 線** × 900 方位 |
| 每掃點數 | **86,400** → **864 k 點/秒** |

| `frame_id` | `rslidar_head` |
| 發布者 | `/rslidar_sdk/rslidar_points_destination_0`，QoS **RELIABLE** / KEEP_LAST(100) |
| 訂閱者 | 5 個（`robot_slam`、`localization`、`perception_jobs`…） |

### 光達的連線方式（★ 文件勘誤）

| | |
|---|---|
| 前光達 | Orin NX 的 `enxc817f52c3f92`，網段 `192.168.1.0/24`，**板端位址 192.168.1.102** |
| 後光達 | Orin NX 的 `enxc817f52c3f2c`，網段 `192.168.2.0/24`，**板端位址 192.168.2.102** |
| UDP 埠 | 兩邊都在收 `6699`（msop）、`7788`（difop）、`6688`；前光達 `6699` 的 Recv-Q 有 2176 |
| 流量 | 每張網卡 2.88 MB/s ≈ 23 Mbps |

⚠️ 舊文件（`D1Max_機器狗資訊.md` §3.3）把 `192.168.1.102` / `192.168.2.102` 寫成
「光達的位址」。**那是 Orin NX 自己兩張 USB 網卡的位址**，光達在同網段的另一個位址上。
所以從 RK 或從 PC ping `192.168.1.102` 一定不通（沒有路由），從 NX ping 一定通（是自己）。
**光達真正的 IP 要看 `rslidar_sdk` 的設定檔，這趟沒找到那個檔**（檔名是 `config.yaml`，
第一趟只用檔名 pattern 找，已改成按內容找）。
