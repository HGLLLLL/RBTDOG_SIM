## 0. 一句話

**「找一組穩定行走不會跌倒的 CPG 步態」這件事，`walk` 已經達成而且複驗過了。**

RL 那條線才有一個不會被順手改掉的起點與對照組。

## 3. 已知限制 —— **不要當作已解決**

1. **走不直。** 偏航 −0.5 ~ −0.9 °/s，180 秒累積 −51°、側偏 −10.7 m。
   **開迴路調參繞不過去**，證據有三：
   - `x_off` 在 20 mm 範圍內掃，偏航率 −0.858 ~ −0.814 °/s，**完全不變號**
   - `d_step` 單調（0.100→−0.06、0.130→−0.85 °/s），**沒有過零點**
   - `ω` 在 1.8 變號（+0.68）但 2.0 又變回來（−0.87）—— **那是分歧不是趨勢**

   → 這正是 CPG-RL 那條線要解的主要問題（見 `CPG-RL_D1Max_設計_2026-08-27.md`）。

   好消息：`walk_fast` 的區間斜率 0–20 s −0.97、20–60 s −0.79、**60–120 s −0.097** °/s
   —— 航向轉過約 −57° 之後幾乎就停住了。要對付的是**起步 1–2 分鐘的一次性航向偏移**，
   不是等速漂移。

2. **只在平地驗過。** 斜坡、台階、不平地面**完全沒測**。
3. **模擬質量比規格書輕 2.2 kg**（MJCF 38.821 vs 規格書 41 kg，可能是沒算雙電池）。
   增益與配平是照 38.8 kg 調的。
4. **`STATIC_SAG` 與 `KP3` 綁死**，改增益必須重掃（不是重跑 `--stand` 就好）。
5. **實機一步都沒走過**，連承重站立（M7）都還沒做。本文所有結論**只在模擬內成立**。

## 5. 度量的坑（引用數字前先看這段）

**不要用 `speed_path` 當行進速度。** 它是逐控制步累加的路徑長，
把機身每一步的左右搖擺全算成前進，**實測高估 68%**：

| walk 20 s | 值 |
|---|---|
| 帳面 x 速度 | 0.143 m/s |
| ★ 行進速度 `speed_travel` | **0.148 m/s** |
| 路徑速度 `speed_path`（舊） | 0.249 m/s |

那一次偏航只有 +7.9°，`cos(7.9°) = 0.99` —— 68% 的差距不可能來自轉彎，只能來自搖擺。

**偏航率不能用「總偏航 ÷ 總秒數」。** 起步暫態（前 20 s +8°，方向與後面相反）
會**永久稀釋**後面的斜率：60 秒那格看起來像「不漂」，120 秒一跑 12 次全部落在
−46.9 ~ −25.4°，沒有一次靠近零。要看**區間斜率**。

**偏航不能拿來挑參數。** 12 擾動下它的格內全距 3.6–11.7°，佔訊號 20–60%。
平均俯仰的全距只有 0.01–0.02°、佔 2% —— 配平只能看俯仰。

## 6. 怎麼重現

```bash
bash task7/model/zgws/fetch_assets.sh     # 先取回 54 MB 網格（未進版控）

# 單次
conda run --no-capture-output -n rbtdog \
  python task7/inference/cpg_walk_max.py --gait walk --video

# 多擾動複驗（本文 §2.2）
conda run --no-capture-output -n rbtdog \
  python task7/inference/cpg_sweep_max.py --plan base --seeds 12 --procs 2

# 回歸測試
conda run --no-capture-output -n rbtdog python -m pytest task7/tests/ -q
```

⚠️ 掃描的 worker 數由**可用記憶體**反推（每個 1.5 GB + 保留 2.5 GB），
`--procs` 給多少都會被壓下來。2026-08-26 曾經因為「每個 rollout 重建 1.15 GB 的 MJCF」
把 15 GB 的開發機 OOM 弄當機，那個根因已修（模型快取 + 每次還原可覆寫欄位）。
