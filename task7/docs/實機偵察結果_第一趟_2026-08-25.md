## 1. ★★★ 底層介面存在 —— 但名字不是 `spline_shm`

RK3588 的 `/dev/shm`：

```
-rw-r--r--  root root  1048576   joint_cmd      ← 關節指令
-rw-r--r--  root root  1048576   joint_state    ← 關節狀態
-rw-r--r--  root root  1048576   imu_central    ← IMU
（另有約 30 個 ecal_* 的 IPC 段）
```

- 三個檔各 **1 MB**（D1 EDU 的 `spline_shm` 是 10240 B、`imu_shm` 1024 B，這台大得多）
- 權限 `-rw-r--r--` `root:root` → **非 root 可讀、寫入需要 root**（與 D1 EDU 同樣態勢）
- **架構與 D1 EDU 相同，命名不同。** 這是「路線 C」成立的直接證據

⚠️ 尚未驗證的：結構、更新頻率、是不是活的串流、`joint_cmd` 寫進去 daemon 認不認。
第二趟會撈快照回來離線分析。

Orin NX 的 `/dev/shm` 只有 nvidia 的 `nvsci*` / `ipc_test*`，**沒有任何運控相關**。

## 5. ⚠️ 這趟的失敗：ROS2 整段沒跑到

兩塊板的 log 都停在 `cat /opt/runtime/env.bash` 之後。

**成因**（已在本機重現）：

```bash
set -u                                   # 偵察腳本開頭
. /opt/runtime/env.bash                  # env.bash 第 2 行：
#   export LD_LIBRARY_PATH=$LD_LIBRARY_PATH:/opt/runtime/lib
#   非互動 SSH 下 LD_LIBRARY_PATH 未設 → unbound variable → shell 離開（碼 127）
```

再加上腳本寫了 `2>/dev/null`，錯誤訊息也被吞掉 → **看起來像正常結束**。

**修法**：把 source 包進 `set +u` 的 subshell，且不吞 stderr。
`recon_d1max.sh` 與新的 `recon2_d1max.sh` 都已修正並在本機驗證。

**教訓（值得記住）**：
`set -u` 是好習慣，但**碰到「source 別人的環境腳本」就是地雷** ——
ROS / conda / 各種 SDK 的 setup 幾乎都會引用未設變數。
一律用 `( set +u; . xxx )` 包起來，而且**不要吞 stderr**，
否則失敗會偽裝成成功。
