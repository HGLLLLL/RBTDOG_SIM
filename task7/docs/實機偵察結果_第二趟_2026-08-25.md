## 0. 一句話結論

**底層控制介面存在、結構已解出、而且我們從模擬器發布包推定的原廠參數得到實機證實。**

`/dev/shm/joint_cmd` 是一個 **16 × {position, velocity, effort, kp, kd}（float64）** 的
共享記憶體區，正好對應 `ros2_control` 實機列出的 command interface。
**這就是 D1 Max 的 low-level 介面**，只是名字不叫 `rt/lowcmd` 也不叫 `spline_shm`。

**尚未做的：寫入。** `joint_cmd` 是 `root:root -rw-r--r--`，非 root 寫不進去。

## 1. 控制鏈路（已由三個獨立證據交叉確認）

```
        mc_ctrl (運控，ROBOT_TYPE=ZGWS)
             │ 寫
             ▼
    /dev/shm/joint_cmd                    16 × {pos, vel, effort, kp, kd}  float64
             │ 讀
             ▼
    joint_shm_controller                  ros2_control controller
    (joint_controller/JointShmController)  ← 佔用（claimed）全部 80 個 command interface
             │ 寫 command interfaces
             ▼
    zsi_actuator_driver                   ros2_control hardware
    (zsi_actuator_driver/ActuatorInterface)
             │
             ▼  16 顆馬達
             │
    /dev/shm/joint_state                  16 × {pos, vel, effort, temp, voltage, error}
```

三個證據：
1. `ros2 control list_hardware_interfaces` → 16 關節 × `{position, velocity, effort, kp, kd}`
   共 80 個 command interface，全部 `[available] [claimed]`
2. `/opt/runtime/bin/start_motion_control.sh` **先等 `/dev/shm/joint_cmd` 出現才啟動 `mc_ctrl`**
   → shm 由 ros2_control 端建立，`mc_ctrl` 是寫入者
3. SHM 二進位解碼出來的欄位，與 command interface 的名稱與數量逐項吻合

### 插入點在哪

**`/dev/shm/joint_cmd`。** 所有 command interface 都被 `joint_shm_controller` claimed，
所以「自己 spawn 一個 controller 去搶介面」得先卸載 `joint_shm_controller`——那是活的控制路徑，風險高。
**寫 shm 是原廠自己在用的同一條路**，跟 task6 在 D1 EDU 上做的（凍結 `mc_ctrl` → 直寫 shm）同一個做法。

**額外的好處**：`/joint_shm_controller/joint_cmd_echo` 這個 topic 會把它從 shm 讀到的東西發出來
→ **我們寫進去的指令可以用 ROS2 訂閱驗證**，不必盲寫。task6 當年沒有這個。

## 2. SHM 結構（逆向出來的，解碼器見 `task7/realbot/shm_decode.py`）

三塊都是 **Boost.Interprocess managed segment**，各 1 MiB，內含名為 `SharedVector` 的容器。
佐證：實機設定檔有 `motor_platform_type: 7 # 5 mujoco # 6 shm 7 shmContainer`。

### `joint_cmd`（stride 112）

| 位移 | 型別 | 內容 |
|---|---|---|
| base+0 | u64 | 容器內部欄位（每筆相同） |
| base+8 | char[64] | 關節名（零結尾） |
| base+72 | f64 | **position** |
| base+80 | f64 | **velocity** |
| base+88 | f64 | **effort**（前饋力矩） |
| base+96 | f64 | **kp** |
| base+104 | f64 | **kd** |

第一筆 base = **752**，之後每筆 +112。

### `joint_state`（stride 120）

同上，但數值欄位是 `position / velocity / effort / temp_C / voltage_V`，
末尾多一個 u64 `error`。第一筆 base 同為 752。

### 關節順序（★ 與官方動作設定檔不同）

```
fl1_hip_roll, fl2_hip_pitch, fl3_knee_pitch, fl4_foot,
fr1_hip_roll, fr2_hip_pitch, fr3_knee_pitch, fr4_foot,
bl1_hip_roll, bl2_hip_pitch, bl3_knee_pitch, bl4_foot,
br1_hip_roll, br2_hip_pitch, br3_knee_pitch, br4_foot
```

**SHM 是 FL, FR, BL, BR**；而 `zg_wheels-motion_config.yaml` 的動作腳本欄位是
`FRfootCmd / FLfootCmd / RRfootCmd / RLfootCmd`，也就是 **FR, FL, RR, RL**。
**兩個不同層用不同腿序，寫程式時務必按名稱對應，不要按索引。**

### `imu_central`

單一記錄，數值從位移 **824** 起，全部 float64：

```
+824 acc_x, acc_y, acc_z          (m/s²)
+848 gyro_x, gyro_y, gyro_z       (rad/s)
+872 quat_x, quat_y, quat_z, quat_w
```

實測值：acc = (0.046, −0.121, **9.886**)、|a| = 9.887、|q| = 1.000000。

**四元數順序是 `xyzw`**（與 D1 EDU 的 `imu_shm` 一致）：
- 加速度顯示重力在 **+Z**、x/y ≈ 0 → 機身水平
- 用 xyzw 解得 roll **−0.12°** / pitch **−1.61°** ✅ 與加速度自洽
- 用 wxyz 解得 roll **−30.6°** ❌ 與加速度矛盾

⚠️ 這是「取樣當下機身剛好水平」推出來的，不是刻意做的平放實驗。
要當作定論，建議另外做一次「狗確實平放地面」的取樣複核。

## 3. ★★★ 原廠參數得到實機證實

把實機 `/opt/export/config/zg_wheels-user-parameters.yaml` 與我們從
**MATRiX 模擬器發布包**解出來的那份逐行 diff，**只有兩處不同**：

```diff
-motor_platform_type: 5
+motor_platform_type: 7 # 5 mujoco # 6 shm 7 shmContainer

-#joint pos
-abad_stand_pos   : [0., 0., 0., 0.]
-hip_stand_pos    : [0.6, 0.6, -0.6, -0.6]
-knee_stand_pos   : [-1.2, -1.2, 1.2, 1.2]
-abad_liedown_pos : [0., 0., 0., 0.]
-hip_liedown_pos  : [1.4, 1.4, -1.4, -1.4]
-knee_liedown_pos : [-2.4, -2.4, 2.4, 2.4]
```

第一處是模擬 vs 實機的平台開關。第二處是**模擬那份多了站姿/趴姿區塊，實機沒有**。

**其餘全部逐字元相同**——增益、offset、side_sign、限位、`body_height`、`leg_height`、
步態排程參數。

### 這代表什麼

✅ **原廠 RL 增益確認為實機值**：
`FSM_RL_ABAD_Kp 60 / HIP_Kp 120 / KNEE_Kp 120 / Kd 1.0`、輪 `Kp 60 / Kd 0.5`。
（`zg-user-parameters.yaml` 也在機器上但那是別的機型；
`start_motion_control.sh` 有 `export ROBOT_TYPE=ZGWS` → 載入的是 `zg_wheels-*`。）

⚠️ **但要更正一件事**：先前我用 `hip_stand_pos = [0.6, 0.6, −0.6, −0.6]` 當作
「站姿是前後鏡像 X 型」的證據——**那個欄位只存在於模擬那份，實機沒有**。

結論本身仍然成立，但證據換成這兩個：
- `hip_default_pos = [0.8, 0.8, −0.8, −0.8]`、`knee_default_pos = [−1.5, −1.5, 1.5, 1.5]`
  （RL 預設姿）**實機這份有**，同樣是前後反號
- 官方 MJCF 的正向運動學：前後反號那組給出對稱的四輪 x = ±0.3398，
  四腿同號那組會讓後腿整條往後翹

### 另一個獨立驗證：offset 出現在活的 SHM 裡

`joint_cmd` 的 position 欄位讀出來**恰好等於**設定檔的 `abad/hip/knee_offset`：

| | fl | fr | bl | br | 設定檔（FR,FL,RR,RL） |
|---|---|---|---|---|---|
| abad | −0.523 | +0.523 | +0.523 | −0.523 | `[0.523, −0.523, −0.523, 0.523]` ✅ |
| hip | +2.443 | −2.443 | −2.443 | +2.443 | `[−2.443, 2.443, 2.443, −2.443]` ✅ |
| knee | +2.803 | −2.803 | −2.803 | +2.803 | `[−2.803, 2.803, 2.803, −2.803]` ✅ |

四組全中。這同時證明了三件事：**欄位位移解對了**、**設定檔就是實機在用的**、
**`joint_cmd` 是馬達座標系**（控制器角 0 → 馬達角 = offset）。

## 4. 取樣當下的機器狀態

- `joint_cmd` 的 **kp / kd / effort 全為 0** → **馬達在洩力（passive）狀態**
- `joint_state` 的 velocity ≈ −0.001、effort ≈ ±0.03 N·m → 靜止、幾乎不出力
- 溫度 24–25 °C、電壓 53–54 V（雙電池 48 V 系統，合理）
- `error` 欄位 16 顆全是 `1`（意義未知）
- 三塊 shm 兩次取樣 md5 都不同 → **都是活的串流**

⚠️ 用推定的換算式 `馬達角 = side_sign × 控制器角 + offset` 反推 `joint_state`，
得到 abad 0.571 / hip 1.146 / knee −2.738 rad —— 接近機構限位，
**與「洩力癱在限位上」自洽，但不等於任何一組文件姿態，所以換算式仍未證實。**
要確認：讓狗站好（已知姿態）再取一次快照比對。

## 7. 這趟又抓到的腳本 bug（第三個）

判讀回報「❌ ROS2 還是沒載入」，但 log 裡明明有「載入成功 ✅」。

```bash
set -o pipefail
echo "$BODY" | grep -q "載入成功"     # BODY 有 2788 行
#   grep -q 命中後立刻結束 → echo 收到 SIGPIPE（離開碼 141）
#   → pipefail 取管線中非零的離開碼 → 整個判斷變成「失敗」
```

**修法**：`grep -q "..." <<< "$BODY"`（herestring，沒有管線）。已修並在本機重現驗證。

**三趟下來的 bash 教訓（都值得跨專案記住）**：
1. `set -u` + `source` 別人的環境腳本 = 地雷（第一趟）
2. 自動判讀的 grep 會打到腳本自己印的區段標題 → 誤報命中（第一趟）
3. `set -o pipefail` + `cmd | grep -q` = SIGPIPE 造成的**誤報失敗**（第二趟）

共同點都是**「失敗或成功被安靜地偽裝」**。診斷輸出本身也需要被驗證。
