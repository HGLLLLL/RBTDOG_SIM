# 現場操作卡（第三趟）：底層寫入與單顆馬達驅動

**這是第一次真的對 D1 Max 寫入指令。** 前兩趟全程唯讀，這趟不是。
出發前整份看過一遍，現場照著做。

- 對象：D1 Max 的 **RK3588**（`192.168.234.1`）
- 物理擺放：**狗肚子墊高、四輪完全離地**
- 預計時間：第一趟 20 分鐘、第二趟 15 分鐘

## ★ 分兩趟做，中間帶資料回來複核

連上狗的 WiFi 就沒有網路，所以**現場沒有人可以問**。
第一次讓馬達動之前應該要有一道複核，所以流程拆成兩趟：

| | 做什麼 | 風險 | 結束後 |
|---|---|---|---|
| **第一趟** | **M0**（唯讀檢查）→ **M1**（零出力寫入） | 馬達不會動 | **把 log 帶回來複核** |
| **第二趟** | **M2**（單顆輪馬達） | 馬達會轉 | 帶 log 回來記錄數據 |

M0/M1/M2 都會**自動把完整輸出存到狗上的 `~/m_logs/`**，不必手動複製貼上。

> 想一趟做完也可以（腳本的判準寫得夠明確，自己判斷得出來），
> 但**第一次動馬達**建議還是走兩趟。多花的只是一次切換網路的時間。

---

## 0. 先確認三件事，缺一就不要開始

1. **狗肚子墊穩、四輪完全離地。** 這台 41 kg，墊高要夠穩，輪子要能自由空轉。
2. **急停在手邊。** 機身急停鈕位置先確認過；遙控器 APP 也開著（軟急停）。
3. **馬達目前是洩力的。** 第二趟量到 16 顆的 `kp = kd = effort = 0`，
   代表原廠現在沒在出力。**如果你先用遙控器讓狗站起來，就不是這個狀態了**
   —— 那樣凍結運控時腿會失去支撐。**保持趴著／洩力再墊高。**

⚠️ 動到寫入之前，建議先確認過原廠對「第三方寫入 `/dev/shm/joint_cmd`」的態度與保固範圍。

---

## 1. 為什麼這條路是安全的（要能對主管解釋）

**插入點是 `/dev/shm/joint_cmd`，那是原廠運控自己在用的同一條路**，不是我們硬挖的旁門：

```
mc_ctrl ──寫──▶ /dev/shm/joint_cmd ──讀──▶ joint_shm_controller ──▶ zsi_actuator_driver ──▶ 馬達
```

我們做的事是「**把 mc_ctrl 暫停，改由我們寫同一塊記憶體**」。

三層保護：

| | |
|---|---|
| **力矩公式** | `τ = kp·(p_des−p) + kd·(v_des−v) + tau_ff`。M1 全部寫 0 → **數學上恆為零** |
| **目標值也安全** | M1 的 `p_des` 寫「當下實測角度」，誤差 ≈ 0。就算力矩公式理解有誤，出力仍接近零 |
| **原廠逾時保護** | `joint_cmd_timeout: 500 ms`（實機設定）。**我們的程式若當掉，500 ms 後 controller 會接手並套用 `estop_kd = 35` 阻尼**，不會失控 |

另外 `SIGSTOP` 只是**暫停**行程不是殺掉 —— `SIGCONT` 就恢復，不必重開機。
（不用 `kill`：殺掉會被 `robot-launch` 重新拉起，反而更亂。）

## 2. 部署腳本到狗上

```bash
cd ~/rbtdog_sim
nmcli con up d1max-wifi && ping -c3 192.168.234.1

scp task7/realbot/{shm_io.py,M0_probe.py,M1_zero_write.py,M2_wheel_spin.py} \
    robot@192.168.234.1:~/
```

四支必須在**同一個目錄**（M0/M1/M2 都 `import shm_io`）。

---

## 3. M0 — 唯讀前提檢查（零風險）

```bash
ssh robot@192.168.234.1
python3 M0_probe.py
```

**不需要 sudo、不寫任何東西。** 它會檢查：

| 檢查項 | 要看到什麼 |
|---|---|
| 結構 | 16 顆關節名稱順序正確（`fl1..4, fr1..4, bl1..4, br1..4`） |
| 更新頻率 | `joint_cmd` / `joint_state` 是活的 |
| 馬達狀態 | **16 顆全部 `kp=kd=tau_ff=0`** ← 這項一定要 ✅ 才能往下 |
| 權限 | `mc_ctrl` PID 找得到、sudo 可用 |

**任何一項 ❌ 就停下來。** 特別是「馬達狀態」：若顯示有關節帶著非零增益，
表示狗還在出力，先讓它趴下／洩力。

---

## 4. M1 — 零出力寫入（極低風險，馬達不會動）

**第一趟做到這裡為止。**

先乾跑（不帶 `--confirm`，不凍結、不寫入）：

```bash
python3 M1_zero_write.py
```

確認預檢都過了，再真的跑：

```bash
sudo python3 M1_zero_write.py --confirm --secs 3
```

它會：`SIGSTOP` 凍結 `mc_ctrl` → 以 200 Hz 寫零增益指令 3 秒 → `SIGCONT` 解凍。

### 怎麼判斷成功

`mc_ctrl` 平常把 `p_des` 寫成各關節的 **offset 常數**（±0.523 / ±2.443 / ±2.803）。
我們改寫成**實測角度**，數值會明顯不同。輸出表格會並排顯示：

```
關節              原本 p_des    我們寫的   現在讀回     kp    kd | 最大|速度|  最大|力矩|
fl1_hip_roll        -0.5230    -1.0935    -1.0935    0.0   0.0 |    0.0010     0.0458
```

**通過的條件**：`寫入後讀回相符 16/16`、`最大力矩 < 0.5 N·m`。

### 想再加一層驗證（選配，需第二台電腦）

`joint_shm_controller` 有 `enable_pub_cmd: true`，會把**它從 shm 讀到的東西**發成 topic。
另開一台電腦訂閱就能看到我們的值被 controller 真的讀走了：

```bash
ros2 topic echo /joint_shm_controller/joint_cmd_echo --once
```

（需 `ROS_DOMAIN_ID=66`、`RMW_IMPLEMENTATION=rmw_zenoh_cpp`。**RK 是 66 不是 24**。）

## 4.5 第一趟收工 — 把 log 帶回來

```bash
exit                                          # 離開狗
scp -r robot@192.168.234.1:~/m_logs ./m_logs_trip3
nmcli con down d1max-wifi && nmcli con up Q500_ForDog
```

`m_logs/` 裡會有 `M0_<時間戳>.log` 與 `M1_<時間戳>.log`。**把這兩個檔給我看。**

我會複核這些腳本自己判斷不出來的東西：

- `joint_cmd` / `joint_state` 的更新頻率是否合理（太低代表有東西不對）
- `mc_ctrl` 有沒有乾淨地凍結（狀態 `T`）與恢復（`S`）
- 16 顆的溫度、電壓、`error` 欄位有沒有異常值
- 零出力期間的殘餘力矩是雜訊還是真的有出力
- `joint_cmd` 的 offset 常數是否與設定檔一致（結構健全性的再確認）

確認沒問題再上去跑 M2。

## 5. M2 — 讓一顆輪馬達轉起來 ★（第二趟）

**再確認一次：肚子墊穩、四輪離地、急停在手邊。**

先乾跑：

```bash
python3 M2_wheel_spin.py --joint fl4_foot
```

再實跑（**從最保守的參數開始**）：

```bash
sudo python3 M2_wheel_spin.py --joint fl4_foot --confirm
# 預設 v_des=0.3 rad/s、kd=1.5、tau_ff=0、2 秒
```

腳本每輪都把**其餘 15 顆壓零**，確保只有目標輪會動。三重保護：
`|速度| > 3.0 rad/s`、`|力矩| > 5.0 N·m`、逾時 2 秒 → 立刻歸零並解凍。
（規格書輪馬達上限 33 N·m，這裡的 5 是極保守值。）

### 三種可能結果

| 輸出 | 意思 | 下一步 |
|---|---|---|
| **角度變化 > 0.05 rad** | ★ 轉了，驗證成功 | 記錄數字，收工 |
| **有力矩但沒轉** | 卡在靜摩擦 | 加前饋力矩：`--tff 0.5`（見下） |
| **力矩幾乎為零** | 指令沒被接受 | 回頭查 M1 是否真的通過 |

**卡靜摩擦時**（task6 在 D1 EDU 上就是這樣）：

```bash
sudo python3 M2_wheel_spin.py --joint fl4_foot --confirm --tff 0.5
# 還是不動就 --tff 0.8，一次加一點，不要一次跳很大
```

⚠️ task6 的經驗：`tau_ff` 掙脫靜摩擦的瞬間會**速度過衝**（D1 EDU 實測衝到 2.39 rad/s
才被 kd 拉回）。所以 `--vmax` 保護不要關掉。這台輪子更大，過衝可能更明顯。

## 6. 第二趟收工

腳本正常結束、Ctrl-C、或例外，都會自動歸零 + `SIGCONT` 解凍。**但還是要確認一次**：

```bash
python3 M0_probe.py            # 看 mc_ctrl 狀態應為 S 或 R（不是 T）
                               # 16 顆應回到 kp=kd=tau=0
```

然後用遙控器讓狗站起來走兩步，確認原廠功能完全正常。

```bash
exit
scp -r robot@192.168.234.1:~/m_logs ./m_logs_trip4
nmcli con down d1max-wifi && nmcli con up Q500_ForDog
```

## 7. 出事了怎麼辦

### 狗有異常動作 / 聲音

**按急停**（機身鈕或遙控器 APP 紅色鈕）。然後：

```bash
sudo kill -CONT $(pgrep -x mc_ctrl)     # 確保運控沒被卡在凍結狀態
```

### 腳本當掉、來不及還原

原廠的 `joint_cmd_timeout: 500 ms` 會接手 → controller 套 `estop_kd = 35` 阻尼。
輪子離地的情況下這是無害的。仍請手動解凍：

```bash
pgrep -x mc_ctrl                        # 拿 PID
cat /proc/<PID>/stat | awk '{print $3}' # T = 還凍著
sudo kill -CONT <PID>
```

### `mc_ctrl` 解凍後行為怪怪的

`robot-launch` 管著它，重啟該節點：

```bash
robot-launch list                        # 找到對應的 egg id
robot-launch restart <id>
```
最後手段是整台重開機。**`SIGSTOP`/`SIGCONT` 不會造成永久性改變。**

### ⚠️ 千萬不要做

- ❌ 不要對**腿關節**（`*1_hip_roll` / `*2_hip_pitch` / `*3_knee_pitch`）下增益。
  M2 用 `choices` 擋住了只允許四顆輪，**不要繞過它**。腿關節要等吊掛。
- ❌ 不要用 `pkill -f` / `pgrep -f` 搭配會匹配到自己命令列的字串（task6 中過兩次，
  一次直接殺掉自己的 SSH）。腳本裡一律用 `pgrep -x`。
- ❌ 不要在 `mc_ctrl` 凍結狀態下離開現場。

---

## 8. 回來要記錄的數字

- M1：寫入後讀回相符幾 / 16、最大力矩
- M2：最大速度、最大力矩、角度變化、用了多少 `tau_ff` 才轉得動
- 靜摩擦掙脫門檻（多少 `tau_ff` 開始有動作）—— 這個值之後會拿去填 MJCF 的
  `frictionloss`（目前 CPG 模擬那邊是猜 0，偏保守）
