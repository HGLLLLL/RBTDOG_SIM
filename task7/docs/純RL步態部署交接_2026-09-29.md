# D1 Max 純 RL 步態部署實作指南

版本 2026-09-29。適用對象：已完成 RL 步態訓練（動作空間為 12 個腿關節 PD 目標角 ＋ 4 個輪速度），需要將 policy 部署到智元 D1 Max 實機的工程師。
本文件描述實機的控制介面、部署用的軟體架構、實作步驟與驗證方法。所有數值均來自實機量測或已驗證的設定檔，出處以 `檔案:行號` 或 `文件 §章節` 標示；規格總表為 `docs/D1Max_機器狗資訊.md`。

---

## 1. 範圍與前提

- 部署目標：在實機上以 50 Hz 執行 policy 推論，輸出 12 個關節位置目標與 4 個輪速度目標，由驅動器以 1 kHz PD 追蹤。
- 部署平台：機器狗運控板 RK3588（Python 3.10.12、numpy 1.21.5；無 torch／onnxruntime／jax）。policy 需匯出為 numpy 可讀的權重檔，推論以純 numpy 實作。
- 控制路徑：直接讀寫運控板 `/dev/shm` 共享記憶體，接管期間暫停原廠運動控制程序。不經 ROS 2／eCAL。
- 已驗證範圍：此路徑已完成 16 顆馬達全控、開迴路步態、兩代 RL policy 上機（trip19、trip22、trip23）。
- 安全前提：所有承重測試依 `docs/現場SOP_通用_2026-08-27.md` §2.2 執行。程式崩潰時，原廠 controller 於 500 ms 後清零指令，機器狗會失力下墜；吊帶是唯一的物理安全網。

## 2. 系統架構

### 2.1 硬體與程序

| 元件 | 說明 |
|---|---|
| RK3588 運控板 | 執行原廠 `mc_ctrl`（1 kHz 寫入 `joint_cmd`）與 `robot_hal_node`（cpu7 專用，isolcpus）。我們的部署程式亦在此執行。ssh `robot@192.168.234.1`（狗端 WiFi）／`192.168.168.168`（有線） |
| Orin NX 應用板 | 建圖、導航、視覺。部署不使用。`192.168.168.100` |
| 驅動器 | 16 軸，1 kHz 執行 `τ = kp·(q_des − q) + kd·(v_des − v) + effort`。`q_des`、`v_des`、`effort`、`kp`、`kd` 即 `joint_cmd` 的 position／velocity／effort／kp／kd 五個欄位；`q`、`v` 為 `joint_state` 的 position／velocity |
| 腿關節馬達 | 12 顆，150 N·m、19.9 rad/s |
| 輪馬達 | 4 顆，33 N·m、125.7 rad/s（URDF 標示 50 N·m 有誤，以規格書為準） |
| IMU | 200 Hz，發布至 `imu_central` |

CPU 配置：推論程序限制在 cpu 0–5。cpu7 保留給 `HwLoop`，cpu6 承載全部 UART 中斷（實測負載 60%）。（`D1Max_機器狗資訊.md` §3.2）

### 2.2 資料流

```
joint_state (200 Hz 讀) ─┐
imu_central (200 Hz 讀) ─┼─► obs 組裝 ─► policy 推論 (50 Hz) ─► 動作映射 ─► q_des(12), v_des(4)
                          │                                                      │
                          │          200 Hz 主迴圈：線性內插 q_des、寫入 joint_cmd、抄寫心跳
                          └──────────────────────────────────────────────────────┘
                                                        │
                                              /dev/shm/joint_cmd ─► 驅動器 1 kHz PD
```

符號定義（全文通用）：

| 符號 | 意義 | 單位／座標 | 對應 `joint_cmd` 欄位 |
|---|---|---|---|
| `obs` | policy 的觀測向量（關節、IMU、指令、上一步動作等） | 依訓練定義 | — |
| `act` | policy 的原始輸出，16 維：前 12 為腿關節動作、後 4 為輪動作 | tanh 後 [−1, 1] | — |
| `q_des` | 12 個腿關節的**位置目標角**（desired joint position）：`q_des = clip(stance_q12 + act_scale·act[:12], LO12, HI12)`。驅動器以 `kp·(q_des − q) + kd·(0 − v)` 追蹤 | rad，控制器座標；寫入前以 §3.4 換算至馬達座標 | `position`（`velocity` 與 `effort` 填 0） |
| `v_des` | 4 個輪子的**角速度目標**：`v_des = wheel_scale·act[12:16]`。驅動器以 `kd·(v_des − v)` 追蹤（kp = 0） | rad/s，模型方向；寫入前乘 `4_foot` 符號 | `velocity`（`kp` 0、`kd` 1.0、`effort` 摩擦前饋） |
| `q`、`v` | 關節實測位置與速度（自 `joint_state` 讀取並換算至控制器座標） | rad、rad/s | — |
| `stance_q12` | 基準站姿（動作為 0 時的 `q_des`），本專案為 hip +0.52／knee −1.20（後腿反號）、ABAD 0 | rad，控制器座標 | — |
| `LO12`、`HI12` | `q_des` 的夾限，取 §3.5 機構限位或更保守的訓練限位 | rad | — |
| `act_scale`、`wheel_scale` | 動作到目標的線性縮放，須與訓練端一致 | rad、rad/s | — |

### 2.3 軟體分層與職責

| 層 | 檔案（`task7/realbot/`） | 做什麼 |
|---|---|---|
| 共享記憶體 I/O | `shm_io.py` | 以固定位移讀寫 `/dev/shm` 三個檔：解析 16 筆記錄、抄寫心跳、保證寫入順序（先目標值後增益）、輪角解纏。任何程式只透過它碰 SHM |
| 座標換算 | `coord.py`、`kin.py` | `coord.py`：馬達座標與控制器座標互換（§3.4 的符號與偏移表）、機構限位表。`kin.py`：單腿正逆運動學（本案的動作映射不需要 IK，但事後分析足端高度會用 FK） |
| 觀測組裝 | `rl_obs_v3.py` | 讀一幀 SHM（`read_frame`）→ 換到控制器座標 → 四元數轉重力向量（`w2b`）→ 依訓練定義排成 obs 向量並正規化 |
| 推論 | `policy_np.py` | 載入 npz 權重檔，檢查維度與雜湊，用 numpy 做 MLP 前向（obs → act） |
| 動作映射 | `gen_v3.py` | act → 12 個關節目標角 `q_des` 與輪命令；每步變化量限制；夾在限位內；統計飽和次數 |
| 主迴圈與安全殼 | `M9_gait.py` | 200 Hz 定時迴圈；起身／增益過渡／走／坐下的階段狀態機；每 4 tick 呼叫一次推論與動作映射；q_des 線性內插；護欄檢查與中止；退回機制；收工 JSON |
| 部署工具 | `push_to_dog.sh`、`pull_from_dog.sh`、`estop_max.sh`、`M_faultwatch.py` | 檔案同步與 sha256 比對；log 回收；急停；背景 10 Hz 故障監看 |

名詞：
- **馬達座標／控制器座標**：同一個關節角的兩套數字。馬達座標是編碼器讀值與 `joint_cmd.position` 用的值，零點在機構限位處、正方向依安裝而定；控制器座標是本專案 MJCF 模型的關節角，零點為腿伸直、正方向統一。兩者相差一個符號與一個常數偏移（§3.4）。policy 的輸入輸出都在控制器座標。
- **npz**：numpy 的多陣列檔案格式，用來把訓練好的權重與部署所需常數打包成單一檔案。**MLP 前向**：把 obs 依序乘過各層權重、經激活函數得到 act，即推論；狗上無 torch，以 numpy 實作。
- **限速／限位夾**：限速為限制相鄰兩步 `q_des` 的變化量；限位夾為 `clip(q_des, LO12, HI12)`。
- **動作映射為何在純 RL 仍然需要**：網路輸出的是 tanh 後的 16 個無單位數字，不是關節角。訓練端一定有一段 `q_des = default_pose + scale·act` 把它變成 PD 目標，那段在訓練程式裡而不在網路裡，部署時必須在狗上以完全相同的式子重做。純 RL 的動作映射只剩：加基準姿勢與縮放、輪子維度換成 rad/s、限位夾、淡入；沒有 CPG、週期表與 IK。
- **心跳（heartbeat）**：`joint_cmd` 每筆記錄開頭的 u64 計數器。原廠 controller 以它判斷命令來源是否存活：持續變化才採用指令欄位，500 ms 未變即清零指令區、腿失力。接管後 `mc_ctrl` 被凍結不再更新，部署程式每個 tick 須自行把 `joint_state` 的 tick 抄入（先寫 payload、最後寫心跳）。它同時是安全機制：程式崩潰或卡住時心跳自然停止，controller 於半秒內放手。

### 2.4 整合概觀：換哪些、留哪些

policy 只是整條鏈中的一個函式（obs → act）。與 policy 形態相關的只有三個模組：觀測組裝、推論的網路形狀、動作映射。其餘全部與 policy 無關，原樣沿用。

```
                 ┌──────────────── 沿用（與 policy 無關）────────────────┐
                 │ shm_io   coord   M9_gait 主迴圈／狀態機／增益過渡／      │
                 │ 護欄／退回／收工紀錄   push/pull/estop/faultwatch        │
                 └──────────────────────────────────────────────────────┘
 joint_state ──► read_frame ──► [obs 組裝] ──► [policy_np 前向] ──► [動作映射] ──► q_des, v_des ──► 內插 ──► joint_cmd
 imu_central     (沿用)          替換 ①          網路形狀 ②           替換 ③                      (沿用)      (沿用)
```

| 模組 | 處置 | 說明 |
|---|---|---|
| ① 觀測組裝 | **替換**（新檔 `rl_obs_<name>.py`） | obs 的欄位、順序、縮放由訓練決定。沿用 `read_frame`（讀 SHM）、`coord.to_ctrl`（座標換算）、`w2b`（重力向量）、腿序與符號表；只重寫串接與正規化那一段。見 §5.2 |
| ② 推論 | **沿用**，網路形狀不同時改三行 | `policy_np.py` 假設 brax PPO 的 (256, 256, 128) swish、tanh 輸出。若網路不同，改 `policy_np.py:86, 93-96` 的層數與輸出寬度檢查；npz 的 key 命名照 §5.1 |
| ③ 動作映射 | **替換**（新檔 `gen_direct.py`） | 現行 `gen_v3.py` 內含 CPG 名目步態與週期表，本案不需要。替換成 `q_des = clip(stance + scale·act[:12])`、`v_des = wheel_scale·act[12:16]`，保留限速、淡入、飽和統計；介面照 §5.3 |
| 主迴圈 `M9_gait.py` | **沿用**，改載入處 | 只改 `--v3` 分支的載入與版面檢查（§5.4）。每 4 tick 呼叫「obs → policy → gen.step」的呼叫結構不變 |
| 護欄值 | **重設** | 機制沿用，數值依影子跟跑峰值 ×1.3 重定（§5.5、§7） |
| 影子跟跑測試 | **重寫** | 骨架沿用 `tests/test_policy_v3_closed_loop.py`，比對對象換成自己的模擬器與 policy（§6.1） |
| 其餘（SHM I/O、座標換算、階段狀態機、增益過渡、內插、退回、急停、部署腳本） | **沿用，不改** | 這些是機器的性質，不是步態的性質 |

沿用部分的架構要點：
- **`M9_gait.py` 是一個 200 Hz 定時迴圈加狀態機**。每個 tick 讀 SHM、依當前階段決定 q_des（起身階段來自餘弦插值，步態階段來自 GaitStream 的內插結果）、寫 SHM、抄心跳、跑護欄。步態階段每 4 個 tick 呼叫一次 `GaitStream._advance`，裡面依序做 obs 組裝、推論、動作映射，並處理退回。policy 型態的差異被包在 `_advance` 呼叫的三個物件裡，外殼看不到。
- **增益過渡與淡入淡出由外殼負責**。policy 不需要學起身與坐下：站立用 kp 250，靜止時降到訓練增益，再用 3 s 把 q_des 從站姿混合到 policy 輸出；停止時反向。policy 只在 GAIT 階段、混合比例達到 1 之後才完整生效。
- **護欄與退回是兩層**。退回（該步動作歸零）處理 policy 自身的軟體問題（NaN、超時、舊幀），不中止；護欄（誤差、速度、力矩、傾角、輪速）處理物理危險，觸發即凍結目標角撐住。兩者都不依賴 policy 內容。
- **部署工具保證「狗上跑的就是驗過的」**：`push_to_dog.sh` 逐檔比對 sha256；npz 內記錄訓練增益與來源雜湊，主迴圈啟動時比對；乾跑不寫入即可檢查全部設定。

## 3. 介面規格

### 3.1 共享記憶體佈局（`D1Max_機器狗資訊.md` §4.2；`shm_io.py:24-76, 141-142`）

三個檔案位於 `/dev/shm/`，各 1 MiB，擁有者 root。讀取不需特權，寫入需 sudo。

| 檔案 | 記錄數 | stride | 位移與欄位（小端 f64，另註者除外） |
|---|---|---|---|
| `joint_cmd` | 16 | 112 B | `+0` u64 心跳 tick、`+8` char[64] 關節名、`+72` position、`+80` velocity、`+88` effort、`+96` kp、`+104` kd |
| `joint_state` | 16 | 120 B | `+0` tick、`+8` 名稱、`+72` position、`+80` velocity、`+88` effort、`+96` temp_C、`+104` voltage_V、`+112` u64 error（正常值 1） |
| `imu_central` | 1 | — | 自 `+824` 起 10 個 f64：acc[3] m/s²、gyro[3] rad/s、quat[4]（xyzw） |

記錄順序（index 0–15）：`fl1 fl2 fl3 fl4 fr1 fr2 fr3 fr4 bl1 bl2 bl3 bl4 br1 br2 br3 br4`。命名規則 `<腿><編號>_<種類>`：1 hip_roll（ABAD）、2 hip_pitch、3 knee_pitch、4 foot（輪）。部署程式啟動時應以名稱比對驗證佈局（`shm_io.verify_layout`）。

注意：官方動作設定檔與訓練用 MJCF 的腿序為 `FR FL RR RL`，與 SHM 不同。跨層對應一律以名稱為準。

### 3.2 心跳與逾時（§4.4；`shm_io.py:36-54, 182-194`）

- `joint_cmd` 每筆 `+0` 的 u64 為心跳，原廠更新率 1000/s，16 筆同值。
- 部署程式每個控制週期將 `joint_state` 當下的 tick 複製至 `joint_cmd`。寫入順序固定為：先寫全部 payload，最後寫心跳。
- `joint_cmd_timeout` 為 500 ms。逾時後 controller 將指令區清零，腿在約 0.5 s 後失力。
- 因此主迴圈不得有任何超過數百毫秒的阻塞：鍵盤輸入用 select 輪詢、RT 期間 `gc.disable()`、迴圈間隔設護欄（預設 0.25 s）。

### 3.3 接管與歸還（§5.2–§5.4）

```
1. 讀取 16 軸當前位置
2. sudo kill -STOP <mc_ctrl pid>          # 狀態 S → T；此後心跳由部署程式維持
3. 第一幀即寫入 q_des = 當前位置、kp = 0、kd = 小阻尼，並抄心跳
4. 升增益 → 執行 → 降增益至零 → 持續補心跳
5. sudo kill -CONT <mc_ctrl pid>          # 人工確認後才執行
```

凍結 200 s 實測無異常。歸還不由程式自動執行：`mc_ctrl` 恢復後會延續凍結前的姿勢命令，若腿已偏離會產生突跳，因此解凍是人工判斷點。

### 3.4 關節座標與符號（§6；`coord.py:56-67, 147-156`，2026-08-25 實機驗證）

SHM 中 position／velocity／effort 為馬達座標。控制器座標定義為與本專案 MJCF 一致（FK 四輪共面驗證，殘差 6.5 mm）。

```
q_motor = s · q_ctrl + offset        v_motor = s · v_ctrl        τ_ctrl = s · τ_motor
```

| 關節 | fl | fr | bl | br |
|---|---|---|---|---|
| `1_hip_roll` s／offset | −1／−0.523 | −1／+0.523 | +1／+0.523 | +1／−0.523 |
| `2_hip_pitch` | −1／+2.443 | +1／−2.443 | −1／−2.443 | +1／+2.443 |
| `3_knee_pitch` | +1／−2.803 | −1／+2.803 | +1／−2.803 | −1／+2.803 |
| `4_foot` | −1／0 | +1／0 | −1／0 | +1／0 |

若訓練模型並非本專案 MJCF，部署前須以至少四個靜態姿勢比對上表（方法：`realbot/M4_pose_capture.py`）。

### 3.6 IMU（§7；`rl_obs_v3.py:74-79`）

| 項目 | 值 |
|---|---|
| 四元數順序 | xyzw（實測定案；官方文件自相矛盾） |
| gyro | rad/s，三軸與 MJCF 同號、無對調 |
| 姿態符號 | +roll 右側低；+pitch 頭低；+gyro_z 左轉（俯視逆時針） |
| 安裝偏置 | pitch −1.24°、roll +0.63° |
| gyro 零偏 | (+0.005, −0.013, −0.001) rad/s |
| 雜訊 std | gyro 0.002 rad/s、重力向量 0.005、joint_pos 0.001 rad、joint_vel 0.2（ABAD/HIP）／0.4（KNEE）rad/s |

重力向量計算：`q_wxyz = q_xyzw[[3,0,1,2]]`，`g_body = R(q)ᵀ·(0,0,−1)`（`rl_obs_v3.w2b`）。部署端不修正偏置，訓練端以隨機化涵蓋（姿態 ±3°、gyro 偏置 ±0.02 rad/s）。

### 3.7 輪子控制模式（`M9_gait.py:1116-1135`；`docs/results/K_輪子系統辨識_M11_2026-09-09.md`、`F_trip17事故_輪阻尼抖振_2026-09-03.md`）

輪速度目標經由驅動器速度環實現：

| 欄位 | 值 |
|---|---|
| kp | 0 |
| velocity | v_des（換算至馬達方向） |
| kd | 1.0（步態段）；0.5（起身、坐下、凍結） |
| effort | 摩擦前饋 0.13·sign(v_des)（可選），夾在 ±33 N·m |

約束與特性：
- kd 上限 1.0。kd ≥ 2 時驅動器離散阻尼迴路自激（無載懸空即發生，時間常數 50–64 ms），kd 3.0 承重時出現 64 Hz、±15 N·m 抖振。此現象在 500 Hz 無雜訊的模擬中不會出現。
- 純速度環穩態誤差 `v_des − v = τ_f / kd`，動摩擦 τ_f 0.13–0.20 N·m（M11 辨識）。摩擦前饋即在 `effort` 寫入 `0.13·sign(v_des)` 抵消它。本專案模擬端兩者都有：MJCF 輪關節 `frictionloss 0.13`，且 env 的輪命令加了同樣的前饋與 |v_des| < 0.3 rad/s 死區（`inference/rl_env_v3.py:118, 463-464`）。部署原則是與訓練端一致：訓練時的控制律有前饋就加、沒有就不加；若訓練模型未建輪摩擦，實機加前饋較接近訓練條件，不加則穩態慢 0.13–0.2 rad/s。
- 不採用「外環於 50 Hz 計算力矩後寫 effort」：腳離地時輪慣量小，50 Hz 外環迴路增益超過 2 即發散（trip22 實測 35 rad/s 觸發護欄）。
- 讀回的輪速須乘以 §3.4 的 `4_foot` 符號才是模型方向。

## 4. 控制迴路設計

### 4.1 時序（`M9_gait.py:340, 371-381, 1376`）

- 主迴圈 200 Hz：讀 `joint_state`／`imu_central`、寫 `joint_cmd`、抄心跳、執行護欄檢查。
- policy 50 Hz（`GAIT_DT = 0.02`）：每四個主迴圈 tick 推進一次。
- 關節目標：在相鄰兩個 50 Hz 樣本之間線性內插至 200 Hz。模擬端為零階保持，此為已知的差異。
- 輪速目標：零階保持。

### 4.2 增益（`D1Max_機器狗資訊.md` §8.1；`M9_gait.py:120, 230-239, 1352-1358`）

| 階段 | ABAD kp | HIP/KNEE kp | 腿 kd | 輪 kp／kd |
|---|---|---|---|---|
| 起身、坐下（原廠站立 FSM 值） | 250 | 250 | 5.0 | 0／0.5 |
| 步態（原廠 RL 走路值） | 60 | 120 | 1.0 | 0／1.0 |

- 步態增益必須與訓練時的模擬設定相同。部署程式讀取 npz 內記錄的訓練增益，與命令列參數比對，不一致即拒絕執行（`M9_gait.py:1138-1142, 1562-1567`）。
- 站立與步態之間的增益切換在機器靜止時以 1.5 s 線性過渡完成（KP_DOWN／KP_UP），kd 隨 kp 以相同比例插值。
- 步態增益下的承重撓度：kp 250 約 15–36 mm，kp 120 相對命令再下沉約 30 mm（M8 與 trip23 FK 實測）。訓練模擬中若使用相同 kp/kd 與正確質量，此撓度會自然出現。

### 4.3 階段狀態機（`M9_gait.py:711-727`）

| 階段 | 時長 | 說明 |
|---|---|---|
| RAMP_UP | 2.0 s | 趴姿，kp 0 → 250 |
| GO_crouch → HOLD_crouch → GO_stand | 1.5 s ×3 | 餘弦插值至站姿 |
| READY | 等待 Enter（逾時 `--hold-max`） | kp 250 站立 |
| KP_DOWN | 1.5 s | 250 → 步態增益 |
| GAIT_IN | `--ramp` 3.0 s | 站姿與 policy 目標 smoothstep 混合；速度指令為 0 |
| GAIT | 等待 Enter（逾時 `--walk-max`） | 進入後 1 s 才施加速度指令 |
| GAIT_OUT | 3.0 s | policy 動作歸零、淡出回站姿 |
| KP_UP → STOPPED | 1.5 s → 等待 Enter | 回 kp 250 |
| SIT_* → RAMP_DOWN | 1.5 s ×3 → 2.0 s | 坐回趴姿、kp → 0 |

Enter 為單步推進；任一等待階段逾時自動前進而非中止。GAIT_IN 期間按 Enter 直接進入 GAIT_OUT。

## 5. 實作步驟

### 5.1 匯出 policy（參考 `inference/export_policy_v3.py`）

npz 內容（`policy_np.py:73-101`）：

| key | 說明 |
|---|---|
| `mean`, `std` | 觀測正規化，shape (obs_dim,) |
| `W0..W3`, `b0..b3` | MLP 權重。現行載入器固定為 (256, 256, 128) swish、輸出層寬 2·act_dim 取前 act_dim 後 tanh（brax PPO 慣例） |
| `obs_dim`, `act_dim`, `layout`, `src_sha256` | 版面與來源雜湊，載入時檢查 |
| `stance_q12`, `LO12`, `HI12` | 動作映射的基準姿勢與限位（控制器座標） |
| `gains`（kp3／kd3） | 訓練增益，供「說兩次」比對 |
| `act_scale`, `wheel_scale`, `ctrl_dt`, `ramp_steps` | 動作縮放與時序常數 |

原則：部署端不含任何硬編碼常數，全部由 npz 提供，確保實機執行的即為離線驗證的組態。
若網路結構不同於上述慣例，修改 `policy_np.py:86, 93-96`（層數與輸出層寬度的檢查）。

### 5.2 觀測組裝（新增 `rl_obs_<name>.py`）

沿用 `rl_obs_v3.py` 的 `Frame`、`read_frame`（SHM 讀取）、`w2b`、`coord.to_ctrl` 與腿序對應；僅依訓練時的觀測定義重排欄位與縮放。標準流程：

1. `read_frame` 取得 16 軸 position／velocity、IMU quat／gyro、tick。
2. 腿關節：`coord.to_ctrl` 換算至控制器座標；速度乘 `s`；減去 `stance_q12`（若訓練如此定義）。
3. 輪速：乘 `WHEEL_SIGN4`。
4. 姿態：quat xyzw → wxyz → 重力向量；gyro 直接使用。
5. 依訓練定義串接指令、上一步動作等欄位；以 `mean`／`std` 正規化。

觀測欄位順序、單位與縮放須與訓練端逐項對照，並以 §6.1 影子跟跑驗證。

### 5.3 動作映射（新增 `gen_direct.py`，取代 `gen_v3.Gen`）

**背景**。現行主迴圈在步態階段每 50 Hz 呼叫一次「產生器」物件，把 policy 輸出換成關節目標與輪命令。現行產生器是 `gen_v3.Gen`，內含 CPG 名目步態、原廠週期表與 IK，本案不需要這些。主迴圈並不知道產生器內部怎麼算，只透過固定的幾個方法與屬性使用它（Python 鴨子型別）。因此做法是：**新寫一個類別，提供相同名稱的方法與屬性，內容換成純 RL 的映射；主迴圈不必改**。

**主迴圈使用的介面**（出處 `M9_gait.py:542-676`）：

| 成員 | 主迴圈拿它做什麼 | 純 RL 版本應提供 |
|---|---|---|
| `stance_q12()` | 起身的目標姿勢、淡入的起點、零動作時的目標 | 訓練時的 default pose（控制器座標，12 維） |
| `step(cmd, act, v_wheel)` → `(q_des12, tau4, c)` | 每 50 Hz 呼叫一次。`cmd` 為速度指令 (vx, vy, wz)，`act` 為 policy 輸出（退回時為全 0），`v_wheel` 為四輪實測速度。回傳的 `q_des12` 送去內插與寫入，`tau4` 寫入輪子的 `effort` 欄 | `q_des = clip(stance + scale·act[:12])`；`tau4` 給摩擦前饋或 0 |
| `v_nom` | kd1 輪模式的 `velocity` 欄（§3.7） | `wheel_scale·act[12:16]` |
| `v_meas` | 外環用的實測輪速；kd1 模式不使用 | 直接存 `v_wheel` |
| `cmd_prev` | 上一步的指令，供 obs 組裝與鏡像判斷 | 記錄上一步 `cmd` |
| `integrate_head(gyro_z)`、`head_err`、`s4`、`s_arc`、`c` | v3 的 obs 需要的產生器內部狀態（航向誤差積分、相位） | 本案 obs 由自己的模組組裝，這些可回傳 0／空值；`integrate_head` 留空 |
| `n_clamp`、`n_sat`、`sat_mask` | 收工 JSON 的統計：IK 縮限次數、限位飽和步數、該步被夾的關節 | `n_clamp` 固定 0；`sat_mask` 為 `q_raw != q_des`；`n_sat` 累計 |

**範例實作**（常數全部由 npz 提供，見 §5.1）：

```python
import numpy as np

class Gen:
    def __init__(self, P):                       # P：npz 讀出的常數
        self.stance = np.asarray(P["stance_q12"], float)
        self.lo, self.hi = np.asarray(P["LO12"]), np.asarray(P["HI12"])
        self.act_scale = float(P["act_scale"])   # rad，與訓練端相同
        self.wheel_scale = float(P["wheel_scale"])  # rad/s
        self.ramp_steps = int(P["ramp_steps"])   # 淡入步數，例 50 = 1 s
        self.slew = float(P.get("q_slew", 0.05)) # 每步 q_des 最大變化量，rad
        self.i = 0
        self.q_prev = self.stance.copy()
        self.cmd_prev = np.zeros(3); self.head_err = 0.0; self.s4 = np.zeros(4); self.s_arc = 0.0
        self.c = {}; self.n_clamp = 0; self.n_sat = 0
        self.sat_mask = np.zeros(12, bool); self.v_nom = np.zeros(4); self.v_meas = np.zeros(4)

    def stance_q12(self):
        return self.stance.copy()

    def integrate_head(self, gyro_z):            # 本案 obs 不用航向誤差
        pass

    def step(self, cmd, act, v_wheel):
        u = min(1.0, self.i / self.ramp_steps)                     # 淡入 0 → 1
        q_raw = self.stance + self.act_scale * u * np.asarray(act[:12], float)
        q_raw = self.q_prev + np.clip(q_raw - self.q_prev, -self.slew, self.slew)   # 限速
        q_des = np.clip(q_raw, self.lo, self.hi)                   # 限位夾
        self.sat_mask = q_raw != q_des
        self.n_sat += int(self.sat_mask.any())
        self.v_nom = self.wheel_scale * u * np.asarray(act[12:16], float)
        self.v_meas = np.asarray(v_wheel, float)
        tau4 = np.zeros(4)                                         # 摩擦前饋由 M9 的 kd1 路徑加
        self.q_prev = q_des; self.cmd_prev = np.asarray(cmd, float); self.i += 1
        return q_des, tau4, self.c
```

**要點**：
- `act_scale`、`wheel_scale`、`stance_q12` 必須與訓練程式的動作映射逐字相同，這是 sim-to-real 的第一道對齊。
- 淡入 `u` 讓起步前 1 s 內 policy 目標從站姿漸入，配合主迴圈 GAIT_IN 的 3 s smoothstep，避免第一步跳躍。
- 限速值以訓練時的最大單步變化決定，設得比它大即可；目的只是擋住異常輸出。
- 退回時主迴圈傳入 `act = 0`，此時 `q_des` 回到 `stance_q12`、`v_nom` 為 0，即「零動作＝站姿」。
- 輪子的最終寫入由主迴圈的 `--wheel-mode kd1` 路徑完成（`M9_gait.py:1116-1135`）：`velocity = v_nom`（換馬達方向）、`kd = --wheel-kd`（1.0）、`effort = tau4 + 摩擦前饋`，夾 ±33 N·m。

## 8. 安全程序

### 8.1 承重測試前提（SOP §2.2、§2.3）

- 吊帶掛設為「鬆弛但塌下可承接」，高度低於 292 mm（實務 260 mm）。過緊會分擔承重使力矩量測失真；過高則腿懸空，數據無效。
- 電壓 > 53 V；場地淨空 ≥ 5 m；急停鈕與電源開關位置確認。
- 至少一人不接觸機器，負責急停。
- 第二個終端機已登入運控板，命令列停在 `sudo bash ~/estop_max.sh`。

### 8.2 中止語意

承重狀態下中止一律為「凍結目標角、維持增益」。洩力等同機器直接墜落。僅在吊掛不承重的測試中使用純阻尼中止。

### 8.3 急停腳本（`estop_max.sh:48-113`）

1. 終止 `WRITERS` 清單內的部署程序（SIGTERM，0.3 s 後 SIGKILL）。
2. 確認程序已終止，並檢查 `/proc/*/maps` 無其他非原廠程序映射 `joint_cmd`。失敗則拒絕解凍並提示切斷電源（避免與原廠同時寫入指令區）。
3. `kill -CONT mc_ctrl`，列印 16 軸增益狀態。

執行後腿於約 0.5 s 失力，腿下方不得有人。

### 8.4 每次執行後

程式列印 `sudo kill -CONT <PID>`，人工確認機器狀態後執行。未解凍即進行下一次執行會導致 `mc_ctrl` 狀態異常。
